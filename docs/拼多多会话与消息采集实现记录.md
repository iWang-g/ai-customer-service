## 1. 实现结论

- 完成日期：2026-07-28
- 对应阶段：阶段 C“会话和消息采集”
- 当前状态：代码、沙箱 preload、RPA 队列、服务端入库和多店隔离自动化验证均已通过
- 下一阶段：阶段 D“消息发送闭环”

阶段 C 已接通以下链路：

```text
拼多多接待页 DOM
  -> 店铺专用沙箱 preload
  -> Electron 主进程校验和账号维度补全
  -> Python RPA SQLite 离线队列
  -> FastAPI 幂等入库
  -> WebSocket 通知消息中心刷新
```

当前自动采集所有可见会话摘要，以及当前打开会话中已经加载到 DOM 的消息。采集器不会自动点击其他会话，也不会自动点击“加载更多”，避免改变平台未读状态或打断人工客服操作。

## 3. Electron 页面适配器

新增目录：

```text
apps/desktop/electron/platform-workspace/pinduoduo/
  detector.js
  preload.cjs
  reader.js
  runtime.js
  selectors.js
```

职责如下：

- `selectors.js`：维护真实页面优先的选择器目录，并通过只读启动参数传给 preload。
- `preload.cjs`：运行在 `sandbox: true`、`contextIsolation: true` 的第三方页面环境中，读取 DOM 并单向发送预定义事件。
- `detector.js`：识别登录页、接待页、风控页和非拼多多页面。
- `reader.js`：限制字段类型、文本长度、数组数量和允许的消息类型。
- `runtime.js`：补充 `platform_account_id`，生成稳定事件 ID 和幂等键，并处理账号绑定前的快照暂存。

Electron 主进程会保留尚未收到 Python `event_queued` 确认的事件。RPA 子进程异常重启后，这些事件会自动重放；Python 收到后先写 SQLite，再返回确认，因此短暂的子进程重启不会造成页面事件丢失。

preload 使用 `MutationObserver` 监听页面变化，并每 15 秒做一次低频校验。页面没有向第三方 JavaScript 暴露 `ipcRenderer`、Node.js、文件系统、业务 JWT 或 RPA 节点令牌。

工作区顶部会显示：

- 采集待启动
- 正在监听
- 采集正常
- 等待登录
- 需要人工验证
- 采集异常
- 采集已暂停

本地账号注册表升级到 v3，新增 `externalAccountId` 和 `platformAccountName`。旧店铺 ID 和 Electron partition 保持不变，不影响已经验收的登录隔离。

## 4. 事件和幂等

会话摘要使用 `conversation_snapshot` 事件；当前会话消息根据方向使用 `message_received` 或 `agent_message`。

消息幂等键：

```text
pinduoduo:<platform_account_id>:<conversation_external_id>:message:<platform_message_id>
```

没有稳定消息 ID 时，使用发送方向、正文、平台时间和时间标签的摘要作为降级键。会话摘要幂等键包含会话当前名称、最新消息、未读数和头像摘要状态，DOM 没有变化时不会重复入队。

服务端增加两层去重：

1. `rpa_events` 按当前用户的 `event_id` 或 `dedup_key` 去重。
2. `messages` 在同一业务会话内按 `platform_message_id` 再次去重。

会话查找包含：

```text
user_id + platform_account_id + platform_code + external_conversation_id
```

因此两个店铺即使出现相同买家 ID、会话 ID和消息 ID，也不会合并。

## 5. 自动化验证

新增命令：

```powershell
pnpm --dir apps/desktop test:pdd-collector
pnpm --dir apps/desktop smoke:pdd-adapter
pnpm smoke:phase-c
```

验证内容：

1. 平台账号绑定完成前快照留在 Electron 内存中，绑定后再补发。
2. 相同 DOM 快照不会重复产生本地事件。
3. 两个店铺使用相同会话和消息 ID 时，幂等键仍然不同。
4. 沙箱 preload 可按真实拼多多 DOM 结构读取买家消息和客服消息。
5. 服务端生成两个独立会话，每个会话只生成一条消息。
6. 相同 `dedup_key` 换新事件 ID 重放不会重复入库。
7. 相同平台消息 ID 换新事件和幂等键上报，消息层仍不会重复入库。

## 6. 人工验收步骤

1. 启动 `pnpm dev` 并登录桌面端。
2. 右键消息中心左侧“拼多多”，打开原平台工作区。
3. 选择已经登录的店铺，确认顶部显示“正在监听”或“采集正常”。
4. 在拼多多接待页打开一个有历史消息的会话。
5. 回到消息中心，确认出现该店铺的会话摘要和消息。
6. 从买家侧发送一条新消息，确认消息中心自动刷新。
7. 切换另一个店铺并重复步骤 4 至 6，确认两店数据不合并。
8. 重启桌面端后登录，确认服务端保存的会话和消息仍可读取。

验证码、二维码、短信和平台风险确认仍必须由用户手动处理。
