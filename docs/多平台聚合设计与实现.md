# 多平台聚合设计与实现

> 状态：MVP 设计稿，基于 2026-09-21 当前代码梳理。范围先覆盖拼多多和抖店，目标是把两个原平台工作区放进同一个桌面工作台，不在本阶段重写平台适配链路。

本轮界面布局参考：`D:\software-analysis\kuaihui-ai-customer-service\多平台聚合分析.md`。该分析记录的是已拆包 Electron 应用的静态调用链，本文只借鉴其中已核对的窗口外壳、店铺侧栏、`WebContentsView` 挂载/切换和 bounds 同步方式，不复制其平台配置或未在当前项目实现的平台能力。

这里的参考边界需要明确：参考程序只提供布局和容器层面的启发，不作为当前项目的业务实现模板。当前项目已有拼多多、抖店工作区及原平台页面能力，聚合工作台不重新实现平台登录、消息采集、发送、订单、商品、转人工或页面脚本适配。

## 1. 背景与目标

当前项目已经同时支持拼多多和抖店，但用户进入的是两个相互独立的 Electron 工作区：

- 拼多多工作区由 `PddWorkspaceManager` 创建独立 `BrowserWindow`，渲染页使用 `view=pinduoduo-workspace`。
- 抖店工作区由 `DouyinWorkspaceManager` 创建另一套独立 `BrowserWindow`，渲染页使用 `view=douyin-workspace`。
- 两个工作区都有店铺列表、账号切换、页面后退/前进/刷新、登录态和平台页面容器，但状态、账号列表和 IPC 频道各自独立。
- 消息中心已经能够把拼多多、抖店消息归一到同一套会话模型，但不能直接作为两个原平台页面的承载工作台。

本次改造的最小可用目标是：

1. 用户只打开一个“多平台工作台”窗口。
2. 在同一个顶部栏内查看并切换拼多多、抖店店铺。
3. 切换店铺时显示对应平台的原页面，原有 Cookie、登录态、页面脚本、采集和发送能力继续生效。
4. 保留原平台工作区的核心操作：添加店铺、切换店铺、暂停/恢复、移除/恢复、重命名、刷新和浏览器前进后退。
5. 平台不可用、未登录或页面异常时，状态在聚合栏中可见，不能因为一个平台失败而阻断另一个平台。

本阶段不追求把两个平台的页面 DOM、平台接口或业务流程抽象成完全相同的实现，也不把消息中心、后台管理和原平台页面一次性合成一个复杂大页面。

## 2. 当前实现事实

### 2.1 渲染入口

`apps/desktop/src/main.tsx` 通过 URL query 选择渲染应用：

```text
view=pinduoduo-workspace -> <PinduoduoWorkspaceApp />
view=douyin-workspace    -> <PinduoduoWorkspaceApp platform="douyin" />
其他                     -> AppShell / 消息中心
```

两个平台目前复用 `apps/desktop/src/platform-workspace/App.tsx` 的 UI，但通过不同的 preload bridge 调用不同的 IPC：

```text
拼多多 -> window.pddWorkspace
抖店   -> window.douyinWorkspace
```

这说明前端工作区壳已经具备复用基础，当前真正分裂的边界主要在 Electron 主进程窗口和平台 manager。

### 2.2 主进程与平台 manager

`apps/desktop/electron/main.js` 目前分别实例化：

```text
PddAccountRegistry       + PddWorkspaceManager
DouyinAccountRegistry    + DouyinWorkspaceManager
```

启动 RPA 时两个 manager 都绑定当前用户；退出或登出时由 `desktop:close-platform-workspaces` 分别调用 `closeForLogout()`。

拼多多 manager 的主要职责包括：

- 创建工作区 `BrowserWindow`。
- 为每个本地店铺创建一个 `WebContentsView`。
- 使用 `pdd-*` partition 保存每个店铺的 Cookie 和浏览器资料。
- 通过 `pinduoduo/preload.cjs` 注入采集、API 发送、订单/商品和转人工适配能力。
- 维护采集器、店铺 actor、RPA 任务、会话健康检查和页面状态。

抖店 manager 的主要职责包括：

- 创建工作区 `BrowserWindow`。
- 为每个本地账号创建一个 `WebContentsView`。
- 使用抖店账号专属 partition 和导航策略。
- 维护消息观察、发送、订单/商品探测、转接和 RPA 任务。

两个 manager 都使用“只显示当前店铺 view”的布局模型。拼多多页面区域从 `WORKSPACE_TOOLBAR_HEIGHT` 以下开始，抖店页面区域从固定的 72px 工具栏以下开始。该模型可以保留，聚合层只需要把两个 manager 的页面 view 挂载到同一个窗口并统一布局。

### 2.3 现有 IPC 与 bridge

拼多多和抖店已经各自暴露了近似的工作区操作：

```text
get-state
add-account
select-account
show-account-menu
detect-account-name
rename-account
set-account-paused
remove-account
restore-account
set-overlay-open
go-back / go-forward / reload
state-changed
```

差异主要是频道前缀和平台专属能力。主进程中还存在平台专属的消息发送、商品/订单、转人工和探测 IPC，不能在聚合 MVP 中简单合并为一个无平台参数的通道。

### 2.4 消息中心与聚合工作台的关系

消息中心的 `Conversation` 已包含 `platform`、`platformName`、`shopId`、`localShopId`、`externalConversationId` 等字段，可用于后续“从统一会话跳转到原平台页面”。但本阶段先只做店铺/页面聚合，消息中心仍保持现状，避免把会话列表、自动回复和平台页面同时迁移造成大范围回归。

## 3. MVP 方案

### 3.1 一个窗口，两个平台 adapter

新增一个聚合 manager，暂定名 `PlatformWorkspaceManager`，它拥有一个 BrowserWindow，并协调两个现有 manager 的账号、view 和平台操作。

推荐的职责边界如下：

```text
PlatformWorkspaceManager
  ├─ 聚合窗口生命周期
  ├─ 当前用户绑定
  ├─ 当前平台/店铺选择
  ├─ 统一顶部栏状态
  ├─ 聚合 view 的挂载、显示和 bounds
  └─ 转发平台专属操作

PddWorkspaceManager
  ├─ 拼多多账号 registry
  ├─ 拼多多页面 WebContentsView 创建和销毁
  ├─ 拼多多采集、发送、RPA 和会话健康
  └─ 拼多多平台专属 IPC

DouyinWorkspaceManager
  ├─ 抖店账号 registry
  ├─ 抖店页面 WebContentsView 创建和销毁
  ├─ 抖店采集、发送、RPA 和页面探测
  └─ 抖店平台专属 IPC
```

这里的关键是让现有平台 manager 支持“无窗口壳模式”：仍由 manager 创建和管理平台 `WebContentsView`，但不再各自创建 BrowserWindow；聚合 manager 提供宿主窗口和页面容器。

如果直接改造现有 manager 的窗口归属风险过大，可以先采用过渡实现：聚合 manager 通过平台 manager 暴露的 `getViews()`、`attachHostWindow()`、`detachHostWindow()` 接口接管已创建 view。无论采用哪种实现，平台的 session、preload 和业务任务都不能迁移到 renderer。

### 3.2 聚合页面布局

参考 `D:\software-analysis\kuaihui-ai-customer-service\多平台聚合分析.md` 中已经核对的实现，MVP 应采用“统一工作台外壳 + 左侧店铺侧栏 + 右侧原平台页面”的结构。平台页面不是 React/Vue 子组件，而是主进程挂载到主窗口 `contentView` 的独立 `WebContentsView`。

```text
┌─────────────────────────────────────────────────────────────┐
│ Header：工作台名称 / 当前平台店铺 / 页面操作 / 运行状态      │
├──────────────────────┬──────────────────────────────────────┤
│ WorkspaceSidebar     │ MainContent                           │
│                      │                                      │
│ 搜索店铺              │ 顶部：页面状态、提示条、当前店铺信息 │
│ 平台筛选              │                                      │
│ 全部 / 拼多多 / 抖店  │ #platform-page-host                  │
│ 登录/异常统计         │  └ 当前店铺 WebContentsView           │
│ 店铺卡片列表          │                                      │
│ 加载进度              │ 空态 / 登录提示 / 加载失败遮罩        │
└──────────────────────┴──────────────────────────────────────┘
```

建议尺寸沿用参考实现的比例：Header 约 65-72px，左侧店铺栏约 300-320px，可折叠到窄栏；右侧主内容区占据剩余空间。尺寸是布局参考，不要求复制参考程序的视觉或组件实现。当前项目已有消息中心左侧平台栏，但聚合窗口内还需要一个“店铺侧栏”，不能把消息中心的 72px 平台栏直接当作聚合页面的完整店铺导航。

聚合 Header 先保持轻量，只展示与当前工作台直接相关的信息：

- 工作台名称和当前登录用户（可选）。
- 当前平台、店铺别名和平台账号名。
- 当前页面状态：加载中、已登录、等待登录、采集异常或页面异常。
- RPA/消息接收状态（已有全局状态时复用）。
- 后退、前进、刷新、侧栏收起/展开等页面操作。
- 关闭或隐藏窗口按钮，行为与当前 Electron 窗口规范一致。

暂不加入参考程序中的算力、知识库、店铺上下线、工单、设置、通知中心等业务导航。它们属于现有消息中心或管理后台的职责，后续确有需求时再通过明确的 IPC 接入。

左侧店铺侧栏包含：

- 搜索框：匹配平台、店铺别名、本地账号名和平台账号名。
- 平台筛选：`全部`、`拼多多`、`抖店`，只过滤店铺卡片，不创建窗口。
- 状态统计：全部、已登录/在线、等待登录、异常、已暂停；统计项同时作为筛选器。
- 店铺卡片：平台图标、店铺别名、平台账号名、登录状态、页面运行状态、采集状态和未读提示（有数据时显示）。
- 底部进度：显示店铺页面初始化进度；单个页面超时不能阻塞其它店铺。

右侧主内容区只承载当前选中店铺：

- React 负责提示条、登录/加载/错误遮罩、空状态和工具栏。
- 主进程负责把当前店铺的 `WebContentsView` 设置到 `#platform-page-host` 对应的屏幕矩形。
- 切换店铺时切换各 view 的可见性，将目标 view 置于承载区 bounds 并聚焦；切换本身不销毁旧 view。
- 窗口 resize、侧栏折叠、提示条展开/收起后，renderer 重新计算 host 矩形并通知主进程。

MVP 不做左右同时展示两个平台页面。未选中的店铺 view 可以继续保留在内存中，必要时由平台 manager 做后台心跳或健康检查，但不应缩放到用户可见区域；参考实现中的 1×1 保活策略暂不作为首轮必需能力。

#### 与当前项目拼多多工作区的区别

当前拼多多工作区已经具备单平台店铺切换，不需要重新发明这段能力：

- `PddWorkspaceManager.selectAccount()` 通过 `#ensureView()` 取得或创建目标账号 view，设置 `activeAccountId`，遍历 `views` 调用 `setVisible()`，聚焦目标 `webContents`，然后调用 `#layoutViews()`。
- 拼多多 view 在创建时就加入当前 manager 的 `window.contentView`；普通切店时不会从 `contentView` 移除旧 view。只有暂停、删除、登出等销毁流程才会移除和关闭 view。
- 当前拼多多 `#layoutViews()` 把所有 view 设置为同一个固定工具栏下方的 bounds；用户看到哪个页面由 `setVisible()` 控制。它目前没有根据 React 容器 `getBoundingClientRect()` 定位页面区域。
- 抖店 manager 也在账号 view 创建时挂载到自己的窗口，切换时更新 `activeAccountId` 并由 `layout()` 控制可见性；布局目前是固定从 72px 工具栏以下铺满。

因此，新聚合工作台与当前拼多多切店的**业务动作相同**：保留每个店铺的独立页面，切换当前可见账号。真正新增的是跨平台统一选择和共同宿主：聚合 manager 要在拼多多、抖店两套 view 中按 `${platformCode}:${accountId}` 选出唯一 active view，并让两套 manager 共用同一个 `BrowserWindow`。聚合布局再把当前固定工具栏 bounds 改为由 `#platform-page-host` 实际矩形驱动。每次切换时不应照搬参考程序的“移除旧 view、重新挂载目标 view”细节；沿用当前项目的 view 保留和显隐模式更简单，也能避免反复 attach/detach 带来的状态与焦点问题。

### 3.3 聚合状态模型

renderer 不直接消费两个不同形状的 state，而消费一个带平台字段的统一快照：

```ts
type PlatformCode = 'pinduoduo' | 'douyin';

interface AggregatedWorkspaceAccount {
  id: string;
  platformCode: PlatformCode;
  platformName: string;
  alias: string;
  paused: boolean;
  loginStatus: string;
  runtimeStatus: string;
  collectionStatus: string;
  statusDetail?: string;
  platformAccountId?: string | null;
  platformAccountLogoUrl?: string | null;
  lastOpenedAt?: string | null;
}

interface AggregatedWorkspaceState {
  activePlatform: PlatformCode | null;
  activeAccountKey: string | null;
  accounts: AggregatedWorkspaceAccount[];
  archivedAccounts: AggregatedWorkspaceAccount[];
  navigation: {
    canGoBack: boolean;
    canGoForward: boolean;
    isLoading: boolean;
  };
  rpa: {
    status: string;
    nodeId?: string | null;
    detail?: string | null;
  };
  platformHealth: Record<PlatformCode, {
    accountCount: number;
    onlineCount: number;
    errorCount: number;
  }>;
}
```

账号 key 必须带平台，推荐使用 `${platformCode}:${accountId}`。因为两个 registry 都使用 UUID，短期内不会自然冲突，但显式带平台可以避免后续导入、日志和消息中心跳转时产生歧义。

平台状态归一只负责展示，不覆盖平台原始状态。比如拼多多的 `collectionStatus=login_required` 和抖店的 `statusDetail=等待登录` 都可以映射为聚合栏的“等待登录”，同时在详情或日志中保留原字段。

## 4. 主进程改造设计

### 4.1 窗口生命周期

新增以下主进程对象：

```text
platformWorkspaceManager
platformWorkspaceWindow
```

打开逻辑：

1. 用户登录成功或从消息中心点击“打开平台工作台”。
2. `platformWorkspaceManager.bindUser(userId)` 校验用户并绑定两个 manager。
3. 创建一个 BrowserWindow，加载 `view=platform-workspace`。
4. 两个平台 manager 按需加载账号 view；默认只加载最近打开的一个账号，其余账号保持现有的后台队列策略。
5. 聚合 manager 将当前账号对应的 view 加到 `window.contentView`，设置 bounds 为工具栏以下区域，并隐藏其它 view。

关闭逻辑：

- 关闭窗口时隐藏窗口，保留平台 view 和 session，行为与现有工作区一致。
- 登出或退出应用时按现有顺序停止采集/任务，再调用两个 manager 的 `closeForLogout()`，最后销毁聚合窗口。
- 一个 manager 关闭失败时使用 `Promise.allSettled`，不能阻塞另一个平台和主进程退出。

### 4.2 manager 最小接口

在不迁移平台业务代码的前提下，两个 manager 需要补一组宿主接口：

```js
attachHostWindow(browserWindow)
detachHostWindow()
getMountedViews() // [{ platformCode, accountId, view }]
setActiveAccount(accountId)
setOverlayOpen(open)
getState()
```

平台 manager 内部的 `layout()`/`#layoutViews()` 需要从“设置 view 的完整 bounds”改为接收宿主提供的页面 bounds，例如：

```js
setHostLayout({ x, y, width, height, visibleAccountKey })
```

聚合 renderer 需要提供页面承载区的矩形，而不是让主进程猜测 React 布局：

```text
platform-workspace:page-bounds
  { platformCode, accountId, x, y, width, height }
```

实现方式可沿用参考程序的 `getBoundingClientRect()`：renderer 在 `#platform-page-host` 挂载、窗口 resize、侧栏折叠或顶部提示条高度变化后读取矩形，再通过 preload 发送给主进程。主进程只接受当前 active account 的 bounds，并将其转换为 BrowserWindow content 坐标后调用 `view.setBounds()`。

现有单平台工作区暂时可以继续使用自己的 layout 适配器，聚合工作台上线后再把独立窗口入口切换到同一宿主接口。这样可以让平台 smoke 测试先保持原有入口，降低一次性迁移风险。

### 4.3 聚合 IPC

新增 IPC 只处理聚合层，不替代平台专属 IPC：

```text
platform-workspace:get-state
platform-workspace:select-account { platformCode, accountId }
platform-workspace:set-platform-filter { platformCode | all }
platform-workspace:add-account { platformCode }
platform-workspace:show-account-menu { platformCode, accountId }
platform-workspace:rename-account { platformCode, accountId, alias }
platform-workspace:set-account-paused { platformCode, accountId, paused }
platform-workspace:remove-account { platformCode, accountId, clearStorage }
platform-workspace:restore-account { platformCode, accountId }
platform-workspace:set-overlay-open { open }
platform-workspace:go-back
platform-workspace:go-forward
platform-workspace:reload
platform-workspace:state-changed
```

平台专属功能继续使用已有频道，例如：

```text
pdd-workspace:send-message
pdd-workspace:refresh-customer-orders
douyin-workspace:probe-orders
douyin-workspace:transfer-conversation
```

聚合工作台只需要在需要时把 `platformCode` 和当前账号映射到对应的 bridge 方法；不要在 renderer 中根据 DOM 或 URL 猜平台。

所有聚合 IPC 都要检查：发送方是主窗口、frame 是 main frame、platformCode 属于白名单、accountId 属于当前用户并且确实属于对应 registry。

### 4.4 现有入口的兼容策略

建议保留旧入口一个迭代周期：

- `view=pinduoduo-workspace` 和 `view=douyin-workspace` 仍可用于 smoke 测试和问题回滚。
- 消息中心里的“打开原平台工作区”先改为打开 `platform-workspace`，并带上可选的 `platformCode/accountId` 初始选择参数。
- 聚合入口稳定后，再把旧入口改成内部跳转或标记为调试入口，不立即删除平台 manager 的旧测试能力。

### 4.5 从消息中心左侧平台栏打开

消息中心左侧 `PlatformRail` 是最合适的聚合入口位置。当前平台栏的 `全部`、`拼多多`、`抖店`、`千牛`按钮承担的是消息筛选，平台右键菜单承担的是平台专属操作；“工作台”应作为独立的全局动作，不能复用平台筛选或右键菜单。

建议布局：

```text
┌──────────────┐
│  工作台       │  <- 全局入口，打开/聚焦聚合窗口
├──────────────┤
│  全部         │  <- 消息筛选
│  拼多多       │  <- 消息筛选，右键仍可打开拼多多旧入口
│  抖店         │  <- 消息筛选，右键仍可打开抖店旧入口
│  千牛         │  <- 消息筛选
│              │
│  管理后台     │
│  用户菜单     │
└──────────────┘
```

按钮行为：

1. 单击“工作台”调用 `desktopBridge.openPlatformWorkspace()`。
2. 聚合窗口不存在时创建一个 `BrowserWindow`，加载 `view=platform-workspace`。
3. 聚合窗口已存在但被隐藏或最小化时，只显示、恢复并聚焦，不重复创建窗口。
4. 首次打开不强制选择某个平台；窗口读取按用户保存的 `activePlatform/activeAccountKey`，没有记录时选择最近打开的可用店铺。
5. 入口按钮不改变消息中心当前的 `selectedPlatform`，用户返回消息中心后仍停留在原来的消息筛选。
6. 平台筛选按钮和平台右键菜单继续保留。右键菜单在聚合入口上线初期仍可作为旧平台工作区的回滚入口，后续再决定是否统一改为打开聚合窗口并定位到对应平台。

主进程新增一个窄 IPC，而不是让 renderer 直接拼接窗口 URL：

```text
desktop:open-platform-workspace
  -> platformWorkspaceManager.open(userId, { platformCode?, accountId? })
  -> 返回 { opened: true, reused: boolean }
```

`desktopBridge.openPlatformWorkspace` 的调用方是主窗口 renderer，因此主进程必须校验发送方是 `mainWindow` 的 main frame，并从当前登录会话取得 `userId`。如果当前用户未登录，返回明确错误，不创建空的聚合窗口。

React 侧建议通过 props 传递动作，保持 `PlatformRail` 可测试：

```text
MessageCenter App
  -> MessageCenterWorkspace.onOpenWorkspace
  -> PlatformRail.onOpenWorkspace
  -> window.desktopBridge.openPlatformWorkspace()
```

按钮视觉上使用 `PanelsTopLeft` 或 `LayoutGrid` 图标，和“全部”平台筛选使用不同图标；标签固定为“工作台”，不显示成“全部平台”，避免用户误以为点击后只是切换消息筛选。按钮激活态表示聚合窗口当前可用或刚被打开，不表示消息筛选状态。

## 5. renderer 改造设计

### 5.1 组件拆分

聚合 renderer 建议按参考程序的外壳结构拆成四层，但组件和业务逻辑使用当前项目自己的实现：

```text
AggregatedPlatformWorkspaceApp
  ├─ WorkspaceHeader
  │   ├─ BrandAndWindowControls
  │   ├─ WorkspaceNavigation
  │   └─ RuntimeStatus / UserMenu
  └─ WorkspaceContent
      ├─ WorkspaceSidebar
      │   ├─ AccountSearch
      │   ├─ PlatformFilter
      │   ├─ AccountStatusStats
      │   └─ AccountCardList
      └─ WorkspaceMainContent
          ├─ PageStatusNotice
          ├─ PlatformPageHost // 只渲染空的承载区，不渲染平台 DOM
          └─ Loading / Login / ErrorOverlay
```

现有 `apps/desktop/src/platform-workspace/App.tsx` 中的重命名、恢复、移除、确认店铺名称等 modal 可以抽为通用组件，通过 `platformCode` 选择调用聚合 bridge。平台名称、图标和状态文案放到配置表，不在组件里散落条件判断。平台页面不通过 iframe、React portal 或 URL 嵌入 renderer；`PlatformPageHost` 只负责提供稳定的 bounds 测量节点。平台页面内部的功能按钮和交互继续由现有平台页面实现，聚合 Header 不复制这些平台业务入口。

### 5.2 初始选择和深链接

聚合窗口支持 query：

```text
view=platform-workspace
platform=pinduoduo|douyin
accountId=<local-account-id>
```

打开后先尝试选择指定平台和账号；账号不存在、已移除或已暂停时，回退到最近打开的可用账号，并在状态提示中说明回退原因。

### 5.3 UI 状态规则

- 没有任何账号：显示添加拼多多店铺、添加抖店账号两个入口。
- 只有一个平台有账号：平台筛选仍显示，但不增加无意义的空白页面。
- 当前账号加载失败：保留顶部栏和其它平台 tab，页面区域显示平台 manager 的错误状态。
- 一个账号暂停：不销毁 registry 数据；按现有 manager 逻辑销毁其 view，恢复时再创建。
- 弹窗打开时，聚合 manager 将全部平台 view 隐藏，避免原生 view 覆盖 React modal。
- 页面前进/后退/刷新只作用于当前 active account，不能误操作另一个平台。
- 页面承载区 bounds 变化时，先隐藏当前 view 或暂时设置为旧 bounds，收到合法的新 bounds 后再显示，避免 resize 过程中出现错位或覆盖侧栏。
- 侧栏折叠只改变主内容 host 的宽度，不改变当前账号；恢复展开后继续显示原 view 和页面状态。

## 6. 数据与持久化

本阶段不合并两个 registry 文件，也不修改现有账号表结构：

- 拼多多继续由 `PddAccountRegistry` 管理。
- 抖店继续由 `DouyinAccountRegistry` 管理。
- 聚合层只在内存中拼接 state，并保存最后选择的 `activePlatform` 与 `activeAccountKey`。
- 最后选择建议写入 `app.getPath('userData')/platform-workspace-preferences.json`，按 `userId` 分区，避免多个用户互相影响。
- 不把 Cookie、access token、密码或平台 session 数据复制到聚合 preference 文件。

账号展示别名仍由各自 registry 负责。聚合层显示平台标签，避免两个平台出现同名店铺时用户无法区分。

## 7. 实施顺序

### 阶段 A：宿主能力改造

1. 给 PDD/Douyin manager 增加宿主窗口注入和 view 列举接口。
2. 把窗口创建、view 创建、view bounds、view 可见性拆开，保持现有单平台行为不变。
3. 为两个 manager 增加“销毁指定账号 view，但不销毁 registry/session”的一致接口。
4. 增加 manager 单元级测试，覆盖 active account、暂停、销毁和回退选择。

完成标准：原有 `smoke:pdd-workspace`、`smoke:douyin-workspace` 和平台相关测试继续通过。

### 阶段 B：聚合主进程和 preload

1. 新建 `platform-workspace-manager.js`，接入两个 manager。
2. 新增聚合 BrowserWindow 和 `platform-workspace:*` IPC。
3. 在 `preload.cjs` 暴露 `window.platformWorkspace` 和 `desktopBridge.openPlatformWorkspace()`，不要把两个完整平台 bridge 直接暴露给聚合 renderer。
4. 在 `vite-env.d.ts` 增加统一 state、聚合 bridge 和消息中心打开动作类型。
5. 增加旧入口到聚合入口的开关，默认在开发环境可回退。

完成标准：同一个窗口能显示两平台账号、切换账号，并且窗口关闭/登出不会遗留 view 或 timer。

### 阶段 C：聚合 renderer

1. 新增 `AggregatedPlatformWorkspaceApp`，复用现有 modal 和 toolbar 视觉样式。
2. 增加平台筛选、带平台标识的店铺 tab 和统一状态栏。
3. 接入深链接和最近选择持久化。
4. 在 `MessageCenterWorkspace -> PlatformRail` 增加“工作台”按钮和 `onOpenWorkspace` props。
5. 将消息中心的工作台按钮接到聚合入口；保留平台右键菜单和旧入口作为回滚路径。

完成标准：用户不需要打开两个窗口即可在拼多多和抖店店铺之间工作，弹窗、刷新和导航不被原生 view 覆盖或串台。

### 阶段 D：消息中心联动

这是 MVP 之后的阶段：

- 消息中心会话点击店铺或平台徽标时，打开聚合窗口并定位到对应账号。
- 当前会话可以继续使用消息中心统一回复；“查看原平台页面”才跳转聚合工作台。
- 不改变现有会话、自动回复和消息入库协议。

## 9. 风险与取舍

### 9.1 原生 view 与 renderer modal 的层级

`WebContentsView` 属于 BrowserWindow 原生内容层，可能覆盖 renderer 的弹窗。聚合 manager 必须在 `setOverlayOpen(true)` 时隐藏所有平台 view，关闭弹窗后再恢复 active view。这个逻辑不能只放在 React 中。

### 9.2 bounds 和坐标系

参考实现把 DOM 的 `getBoundingClientRect()` 结果传给主进程，再更新 `WebContentsView` bounds。当前项目需要明确 renderer viewport、BrowserWindow content 区域和屏幕坐标的转换规则；不能直接复用消息中心的 CSS 宽高值。首轮应把 `page-bounds` 的日志和当前 active account 绑定，重点验证窗口缩放、侧栏拖拽、DPI 缩放和最大化后的页面对齐。

### 9.3 两个 manager 的生命周期不同

拼多多有较重的采集器、store actor 和 session health monitor；抖店有观察、发送 journal、订单/商品探测和 transfer controller。聚合层不应重启 manager 来切换平台，只改变 view 可见性和 active account。

### 9.4 账号标识不能只用 accountId

当前两个 registry 都由 UUID 生成本地账号 ID。未来如果支持导入、迁移或其它平台，单独使用 UUID 会让日志、深链接和消息中心跳转难以排查，因此从 MVP 开始使用 `platformCode:accountId` 作为跨层标识。

### 9.5 不合并 session partition

平台登录态必须继续隔离。聚合只合并窗口和选择，不合并 partition，不共享 Cookie，也不把一个平台页面嵌入另一个平台页面的 DOM。

### 9.6 失败隔离

两个平台的账号、页面和任务必须保持独立错误边界。聚合 manager 汇总状态时使用 `Promise.allSettled`，平台 manager 的异常只更新该平台/账号状态；发送和采集仍由原 manager 自己确认结果。

## 11. 后续演进
