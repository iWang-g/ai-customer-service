# 千牛平台接入方案

> 讨论日期：2026-09-08
>
> 本文用于记录千牛接入当前项目的设计方案。当前阶段只迁移已经实测验证的能力：新消息检测、按店铺与会话读取消息、按店铺与会话发送文本。复杂场景先不展开，后续按真实运行结果迭代。

## 1. 背景和目标

当前项目已经以拼多多为主平台实现了账号管理、消息采集、自动回复和发送链路。千牛经过独立研究后，已经验证出一条更接近平台能力的主链路：

```text
OnMessageArrive
  -> 提取 shopUid / cid / messageId / senderUid
  -> readMessages(shopUid, cid)
  -> 精确匹配触发消息
  -> sendText(shopUid, cid, reply)
```

这条链路的关键价值是：不需要切换千牛店铺、不需要切换会话、不需要操作输入框、不需要 UIA，也不需要按 Enter。千牛可以最小化，目标会话也可以不是当前打开会话。

短期接入目标：

1. 将千牛作为和拼多多并列的平台接入当前项目。
2. 千牛不可用时只影响千牛平台，不影响拼多多、微信或其他平台。
3. 先接入已验证的最小能力：检测新消息、读取历史消息、发送文本消息。
4. 统一输出当前项目已有的 RPA 事件和消息模型，便于复用业务服务端、消息中心和自动回复 pipeline。
5. 保留研究工具链，但生产链路需要封装成可管理、可观测、可恢复的本地 worker。

## 2. 已验证能力

### 2.1 新消息检测

已验证从千牛本地日志：

```text
D:\AliWorkbenchData\System\log\app.log
```

监听 `OnMessageArrive`，可以提取：

- `shopUid`：消息所属店铺/接待账号。
- `cid`：千牛单聊会话 code。
- `messageId`：平台消息 ID。
- `senderUid`：发送方 UID。

该能力可用于实时触发，不依赖当前千牛打开哪个店铺或会话。

### 2.2 按 shopUid + cid 读取消息

已验证通过页面 JS bridge 调用 `im.singlemsg.GetLocalHisMsg`，可以在目标会话未打开时读取该会话最近消息。

当前本地实现：

- 页面 hook：`tools/install-qn-bridge-hook.ps1` 安装的 V8 bridge。
- 页面读消息脚本：`tools/qn-read-messages-page.js`。
- 本地 receiver：`qn-im-bridge-hook-server.js`。
- Node 调用封装：`tools/qn-read-messages.cjs`。

读取时必须按 `shopUid + cid` 定位，并校验返回消息的店铺、cid、方向、消息 ID。已验证读取前后当前会话不变。

当前边界：

- 依赖千牛已登录，并且对应店铺页面已加载新版 bridge。
- 当前主要验证本地历史 `GetLocalHisMsg`。
- 远程历史、分页补齐和更复杂消息类型先作为后续迭代。

### 2.3 按 shopUid + cid 发送文本

已验证原生 direct send：

```text
sendText(shopUid, cid, text)
```

可以直接向指定店铺和会话发送文本。该发送不调用：

- 切店铺。
- 切会话。
- `openChat`。
- `insertText2Inputbox`。
- UIA。
- 输入框写入。
- Enter。

当前本地实现：

- 发送封装：`tools/qn-direct-send-service.cjs`。
- 原生探针：`tools/qn-native-submit-probe/build/qn_direct_general_probe_v1.exe`。
- 默认可通过一次性交互式计划任务进入当前用户桌面会话。
- 发送后观察 `app.log` 中的业务回执，确认 `sendStatus=0`、`progress=100`。

当前边界：

- 依赖千牛客户端已启动并登录。
- 依赖当前 Windows 用户交互会话存在。
- 发送内容限制为单行、短文本，避免误发长文本或复杂内容。
- 当前只验证文本消息；图片、商品卡、订单卡等暂不接入。

## 3. 接入原则

千牛不应作为拼多多实现的分支，而应作为独立平台适配器接入：

```text
platform_code = "qianniu"
```

平台隔离原则：

1. 千牛 adapter 独立目录、独立进程或 worker、独立日志、独立状态文件。
2. 千牛失败只上报千牛状态，不阻塞拼多多工作区和拼多多 RPA。
3. 千牛与拼多多共享业务事件协议，不共享平台操作实现。
4. 业务服务端只看到统一后的平台账号、会话、消息和发送结果。
5. 研究脚本可以保留在 `tools/`，但生产运行代码需要从探针脚本整理成可维护模块。

## 4. 推荐架构

### 4.1 总体结构

```text
千牛客户端
  -> app.log / JS bridge / native send
  -> Qianniu Worker
     -> 新消息监听
     -> 会话消息读取
     -> 文本发送
     -> 去重、串行队列、健康检查
  -> RPA 事件队列
  -> Business API
  -> 消息中心 / 自动回复 pipeline
```

拼多多仍保持现有结构：

```text
拼多多 WebContentsView
  -> pinduoduo preload / runtime
  -> PddWorkspaceManager
  -> RPA 事件队列
```

两者只在 RPA 事件协议、账号模型、消息模型和自动回复 pipeline 层汇合。

### 4.2 目录建议

建议新增独立平台目录：

```text
apps/desktop/electron/platform-workspace/qianniu/
  detector.js
  diagnostic-logger.js
  runtime.js
  worker-manager.js
  message-mapper.js
  README.md
```

如果第一阶段不需要 Electron 页面工作区，也可以先从更小的后台 worker 开始：

```text
apps/desktop/electron/qianniu/
  process-manager.js
  worker-manager.js
  diagnostic-logger.js
```

研究工具暂时保留：

```text
tools/qn-read-messages.cjs
tools/qn-direct-send-service.cjs
tools/qn-live-direct-auto-reply-once.cjs
tools/qn-native-submit-probe/
```

后续稳定后再将可复用部分迁入 `apps/desktop/electron/.../qianniu/`，`tools/` 只保留诊断和人工验证脚本。

### 4.3 Worker 职责

`QianniuWorker` 建议负责：

1. 启动和守护 bridge receiver。
2. 监听 `app.log` 增量。
3. 解析 `OnMessageArrive`。
4. 按 `shopUid + cid + messageId` 读取消息。
5. 将消息归一化为当前项目统一事件。
6. 接收发送任务，调用 `sendText(shopUid, cid, text)`。
7. 串行处理发送，避免同一千牛客户端内并发 direct send。
8. 维护去重状态和回执状态。
9. 上报健康状态与诊断日志。

Worker 不负责生成 AI 回复。AI 回复仍由现有业务 pipeline 负责。

## 5. 统一事件模型

千牛新消息应转成当前项目已有的消息事件形态。建议字段映射：

```text
platform_code              = "qianniu"
platform_account_id        = shopUid
conversation_external_id   = cid
platform_message_id        = messageId
customer_external_id       = senderUid 或 cid 中买家 UID
sender_role                = incoming -> customer, outgoing -> agent
message_type               = text
content                    = message.text
received_at                = sendTime 或观察时间
dedup_key                  = qianniu:{shopUid}:{cid}:{messageId}
```

会话快照可以先保持最小：

```text
conversation_external_id = cid
customer_name            = fromNick 或 buyer uid
latest_message_text      = 最新 incoming 正文
unread_count             = 1 或未知时 0
```

历史消息读取返回的最近 N 条可以作为 `message_snapshot` 入库，触发消息本身再作为明确的新消息事件处理。这样能复用现有消息中心和自动回复逻辑。

## 6. 账号模型

千牛账号建议先以 `shopUid` 作为平台账号 ID：

```text
platform_code = "qianniu"
platform_account_id = shopUid
platform_account_name = 千牛 loginID.display 或用户配置的别名
local_account_id = 本地生成 UUID
```

第一阶段可以不做完整账号登录管理，只做“发现已登录账号”：

1. bridge clients 返回当前已加载页面的 `loginID.targetId`。
2. worker 从 app.log 事件中观察到 `3#shopUid`。
3. 本地配置允许用户把 `shopUid` 绑定到项目里的店铺账号。

后续再补：

- 千牛安装路径检测。
- 千牛进程健康检查。
- 多店铺在线状态。
- 店铺别名自动识别。
- 账号解绑和暂停。

## 7. 发送任务模型

业务层发送文本时，千牛 adapter 只接受明确目标：

```json
{
  "platform_code": "qianniu",
  "platform_account_id": "2222303856223",
  "conversation_external_id": "2214525969878.1-2216058631944.1#11001@cntaobao",
  "text": "您好，消息已收到，这边马上为您处理。"
}
```

adapter 内部执行：

```text
validate target
  -> acquire per-client send lock
  -> sendText(shopUid, cid, text)
  -> observe native/business receipt
  -> emit send result
```

失败策略：

- 不自动无脑重试。
- 如果 native outcome unknown，必须标记 `retryAllowed=false`，交给上层人工确认或后续幂等策略处理。
- 如果回执明确失败，可按错误类型决定是否允许重试。
- 同一会话短时间多条自动回复需要上层合并或排队。

## 8. 健康状态和隔离

千牛 worker 至少上报这些状态：

```text
stopped
starting
online
degraded
login_required
bridge_unavailable
native_send_unavailable
app_log_unavailable
error
```

关键隔离点：

1. 千牛 worker 崩溃不退出 Electron 主进程。
2. 千牛 bridge 端口不可用，只影响读消息能力。
3. 千牛 native send 不可用，只影响发送能力。
4. `app.log` 不可用，只影响实时检测能力。
5. 拼多多工作区不依赖任何千牛状态。

建议日志：

```text
logs/qianniu-worker-YYYY-MM-DD.log
logs/qianniu-bridge-YYYY-MM-DD.log
logs/qianniu-send-YYYY-MM-DD.log
```

日志中不记录 Cookie、token、账号密码。消息正文可按当前项目隐私策略决定是否记录，生产环境建议默认只记录长度、hash、messageId 和状态。

## 9. MVP 范围

第一阶段只做：

1. 启动千牛 worker。
2. 检测已登录店铺页面和 bridge 可用性。
3. 监听 app.log 新消息。
4. 按 `shopUid + cid + messageId` 读取并校验新消息。
5. 发出统一消息事件。
6. 接收文本发送任务。
7. 调用 direct send 并确认回执。
8. 接入现有自动回复 pipeline，先固定为文本回复。

第一阶段不做：

- 自动登录千牛。
- 自动安装或升级千牛。
- 自动处理风控和验证码。
- 搜索会话、切换会话、切换店铺。
- UIA 发送。
- 图片、文件、商品卡、订单卡发送。
- 远程历史完整分页。
- 群聊、子账号复杂分流。
- 多台机器协同同一千牛账号。

## 10. 实施步骤

### 阶段 0：接口和协议收口

1. 确认项目平台枚举支持 `qianniu`。
2. 确认 `PlatformAccount`、`Conversation`、`Message`、`RpaEvent`、`RpaTask` 可以承载千牛字段。
3. 定义千牛消息事件和发送任务的最小 JSON schema。
4. 补测试用 fixture，覆盖 `shopUid/cid/messageId` 映射和去重。

### 阶段 1：独立 worker 封装

1. 将 `qn-live-direct-auto-reply-once.cjs` 拆成长期 worker，而不是一次性测试脚本。
2. 将 `qn-im-bridge-hook-server.js` 纳入 worker 生命周期管理。
3. 将 `qn-read-messages.cjs` 和 `qn-direct-send-service.cjs` 封装为 adapter 内部能力。
4. 增加健康检查和诊断日志。
5. 保持所有发送串行，并保留现有回执确认机制。

### 阶段 2：接入 Electron / RPA 管理

1. 主进程新增 `QianniuWorkerManager`。
2. RPA manager 注册 `qianniu` 平台账号。
3. 消息事件进入现有 RPA 事件队列。
4. 发送任务按 `platform_code=qianniu` 路由到千牛 worker。
5. UI 只展示千牛平台状态和会话消息，不要求第一阶段提供千牛工作区页面。

### 阶段 3：自动回复闭环

1. 新消息入库后进入现有自动回复 pipeline。
2. 生成回复后发出 `send_platform_text` 任务。
3. 千牛 worker 完成发送并回写发送结果。
4. 增加会话级去重和短时间合并策略。
5. 增加人工接管、暂停店铺、暂停会话等控制。

### 阶段 4：能力扩展

后续按优先级补：

1. 远程历史和分页读取。
2. 多消息类型解析。
3. 会话列表和店铺状态同步。
4. 图片/文件发送。
5. 原生读消息入口研究，减少对 JS bridge 的依赖。
6. 原生长期发送服务，减少一次性任务成本。

## 11. 风险和处理策略

### 11.1 千牛版本变化

千牛内部对象、bridge 能力和日志格式可能随版本变化。处理策略：

- 启动时检查千牛版本和 hook version。
- direct send 做 preflight。
- 失败时降级为 `degraded`，不影响其他平台。
- 保留诊断脚本，便于重新验证。

### 11.2 bridge receiver 中断

读取消息依赖本地 receiver。处理策略：

- worker 负责启动和守护 receiver。
- 页面心跳断开时标记 `bridge_unavailable`。
- 支持 receiver 重启后页面重新注册。

### 11.3 发送结果不确定

原生调用可能出现 outcome unknown。处理策略：

- 默认不自动重试。
- 记录 requestId、clientId、messageId 和 app.log cursor。
- 用业务回执确认成功后才标记已发送。
- 不确定结果进入待人工确认或后续补偿流程。

### 11.4 平台隔离

千牛实现涉及本地日志、JS bridge 和原生探针，比拼多多更贴近客户端内部实现。处理策略：

- 千牛 worker 独立运行。
- 所有异常只转换为千牛状态和诊断事件。
- 不让千牛异常冒泡到拼多多工作区或主窗口生命周期。

## 12. 当前结论

千牛已经具备接入当前项目 MVP 的技术基础。推荐先落地一个独立 `qianniu` 平台 adapter，把已验证的三项能力迁入：

```text
detectNewMessage
readMessages(shopUid, cid)
sendText(shopUid, cid, text)
```

这条链路已经在真实千牛客户端上验证过：目标会话未打开、当前在其他会话、千牛最小化时，仍可以检测新消息、读取目标会话消息并直接发送回复。

下一步应先做协议和 worker 封装，不急着扩展复杂场景。只要平台边界清楚，千牛 MVP 可以与拼多多并行运行，并逐步接入现有消息中心和自动回复 pipeline。

### 15.3 千牛新消息实时刷新修复

实测发现：千牛新消息到达时，左侧会话列表能及时显示最新消息预览，但如果用户正停留在该会话，聊天区不会立即显示新消息；切到其他会话再切回来后才会出现。

原因是前端实时事件处理之前只把 `message_snapshot` 当作“需要刷新聊天消息”的事件。千牛当前上报的是：

```text
conversation_snapshot
customer_message
```

服务端已经根据 `customer_message` 把消息写入数据库，并更新会话最新消息，所以左侧列表会刷新；但前端没有针对 `customer_message` 主动刷新当前聊天区的 `messages`。

本轮修复为：以下事件都会被视为消息内容变化：

```text
message_snapshot
customer_message
message_received
agent_message
message_sent
```

当 `rpa.events.batch` 包含这些事件时：

1. 优先根据 `affected_conversations` 精准刷新受影响会话。
2. 如果受影响会话就是当前选中会话，则立即调用 `loadMessagesForConversation`。
3. 如果缺少受影响会话信息，则退回到后台刷新会话和当前消息。

预期效果：千牛新消息到达后，如果用户正在查看该会话，聊天区应自动出现新消息，不再需要手动切换会话刷新。

### 15.4 发送耗时分析和体验优化

千牛 direct send 当前是“确认型发送”，不是 fire-and-forget。主要耗时来自：

1. Electron IPC 到千牛 worker。
2. `qn-direct-send-service.cjs` 调用 native probe。
3. native probe 进入千牛进程执行 direct send。
4. 发送后继续观察 `app.log`，等待业务回执确认。
5. 回执确认后再调用 Business API `recordSentMessage` 落库。

用户体感上的 2 到 3 秒主要来自第 2 到第 4 步。为了先改善体验，本轮没有改变底层确认机制，而是把前端行为改为“先提交，后台确认”：

```text
点击发送
-> 立即清空输入框
-> 立即显示发送中气泡
-> 后台等待 direct send 回执
-> 成功后气泡变为已发送
-> 失败后气泡标红
```

这样能缩短用户感知等待时间，同时仍保留 app.log 业务回执确认，避免误把 outcome unknown 当成成功。

下一阶段真正降低底层耗时的方向是常驻 native helper/RPC：

```text
当前：每次发送启动一次 probe/控制器
优化：启动一个长期运行的 native helper，复用进程定位、callback、日志 cursor 和发送锁
```

预期收益：

1. 减少每次发送的进程启动和初始化成本。
2. 复用千牛进程定位结果。
3. 统一串行队列和回执关联。
4. 更容易上报准确的发送阶段耗时。

这属于更大的底层改造，建议单独推进，并保留当前已可用的确认型 direct send 作为回退路径。

## 16. 第四轮实施记录：常驻发送 helper

实施日期：2026-09-08。

本轮目标是继续优化千牛发送链路，同时不推翻已验证的 direct-send 确认机制。

### 16.1 当前实现

已新增一层常驻发送 helper：

```text
Electron 千牛 worker
  -> QianniuDirectSendClient
  -> 常驻 Node helper 子进程
  -> 现有 qn-direct-send-service.cjs
  -> 原生 direct send
  -> app.log 业务回执确认
```

关键点：

1. helper 是长期运行的 Node 子进程，负责接收 worker 的发送请求。
2. helper 内部串行处理发送，避免并发 direct send 互相干扰。
3. helper 返回结构化结果，包含 requestId、native messageId/clientId、receipt_status 以及阶段耗时。
4. 如果 helper 在请求尚未提交前失败，worker 允许回退到现有一次性 direct-send。
5. 如果 helper 已经接住请求，则不再二次发送，避免 outcome unknown 时产生重复消息。

### 16.2 设计边界

当前 helper 只解决：

```text
请求排队
进程复用
阶段观测
发送结果回传
```

它还没有把 C++ 探针改成真正的长驻 RPC 服务。也就是说：

1. 现在是“常驻 Node helper + 复用现有 direct-send”。
2. 下一步才是“把 direct-send-service 内部再下沉成长期 native helper/RPC”。

### 16.3 当前收益

这一步先把 Electron 主进程和消息中心从一次性发送控制逻辑里隔离出来，便于后续继续做：

1. 发送队列。
2. 阶段计时。
3. helper 健康状态展示。
4. 真正常驻 native helper 迁移。

### 16.4 本轮验证

已通过：

```text

npm run test:qianniu-adapter
```

测试覆盖了：

1. 直接 direct-send 的现有行为。
2. helper 成功路径。
3. helper 尚未提交前失败时的 fallback 路径。
4. helper 返回异步结果后，worker 继续维持原有消息中心返回语义。

## 17. 第五轮实施记录：发送闪窗分析和 direct mode 优先

实施日期：2026-09-09。

实测发现：接入常驻发送 helper 后，千牛消息中心发送时偶尔会出现 PowerShell 窗口一闪而过。

### 17.1 原因分析

闪窗不是常驻 Node helper 本身产生的。真正原因是 helper 内部仍复用了原来的 `qn-direct-send-service.cjs`，而该服务默认路径会调用：

```text
PowerShell controller
-> schtasks /IT 交互式计划任务
-> PowerShell task
-> qn_direct_general_probe_v1.exe
```

这条路径最初用于解决 Codex 后台进程不在用户交互桌面时无法访问千牛窗口的问题。计划任务使用 `/IT` 进入当前用户交互会话，Windows 在某些情况下会短暂显示 `powershell.exe` 或控制台窗口；`windowsHide` 和 `-WindowStyle Hidden` 对计划任务启动出来的新进程不一定完全可靠。

接入常驻 helper 后更容易观察到这个问题，主要是因为消息中心每次发送都会稳定触发这条发送链路；并不是 helper 引入了新的 UI 操作。

### 17.2 本轮调整

本轮将千牛常驻发送 helper 的默认发送模式改为 direct mode：

```text
Electron 千牛 worker
-> QianniuDirectSendClient
-> 常驻 Node helper
-> QN_DIRECT_SEND_MODE=direct
-> qn_direct_general_probe_v1.exe --send-once ...
```

也就是说，在 Electron 桌面进程已经运行于当前用户会话的前提下，优先直接启动 native probe，不再默认经过 PowerShell controller 和交互式计划任务。

保留配置开关：

```text
QIANNIU_DIRECT_SEND_MODE
```

默认值为：

```text
direct
```

后续如果发现某些机器或运行环境下 direct mode 无法访问千牛进程，可以显式改回旧的交互式通道。

### 17.3 预期效果

预期收益：

1. 消除或显著减少发送时 PowerShell 窗口闪现。
2. 减少一次 PowerShell controller 和计划任务调度成本。
3. 保持原有 native direct send 和 app.log 回执确认机制不变。
4. 继续维持“已提交请求后不自动 fallback 重发”的安全策略，避免重复发送。

当前仍不是最终的 native RPC 形态。更进一步的优化仍是把 C++ direct-send 探针改成长驻服务，复用千牛进程定位、admission、callback 和回执观察状态。

主要商品字段对应关系：

```text
auctionTitle -> title
sku          -> 规格字段
buyAmount    -> quantity
picUrl       -> image_url
auctionId    -> 商品 ID（字符串）
subOrderId   -> 子订单 ID（字符串）
price        -> 商品价格字段

```

规格、价格及子订单字段在实现时为现有 products_json 补充明确类型，避免继续用无约束对象在组件内猜测。金额在读取和映射阶段采用十进制字符串或明确的最小货币单位处理；与现有金额契约衔接时统一核对单位。缺失的实付、优惠不能填零，也不能拿 orderPrice 冒充 paid_amount。没有独立证据的签收时间、下单时间不从其他时间字段推断。

目前 `StatusPanel.tsx` 的订单展示和刷新按钮受 `isPinduoduoConversation` 限制，且只读取 `products_json[0]`。本轮应只解除客户订单已支持平台的限制，增加千牛数据来源与刷新分支，支持一笔订单逐件展示商品和规格。拼多多专有的主动话术状态继续按原平台规则展示。

### 18.5 加载、缓存和异常处理

1. 按 2026-09-09 后续确认的规则，切换会话或打开右栏订单页签时只读取项目数据库中已保存的订单，不自动请求千牛。普通新消息刷新也不触发订单采集。
2. 仅手动点击刷新时查询千牛，并将成功结果持久化。取消原计划的 60 秒过期自动刷新；没有已保存结果时显示“尚未采集客户订单”，由用户手动刷新。采集时间属于读取时间，不代表平台订单修改时间。
3. 并发相同买家查询按平台账号和 CID 合并，防止切换、刷新按钮与后台事件重复发请求。不同账号即使买家相同也不能共用缓存。
4. 请求携带会话身份和请求标识；切换到其他会话后，旧请求只能更新其自身缓存，不能覆盖当前会话的订单、错误提示或加载状态。同一目标的旧响应不能覆盖较新的查询结果。
5. 千牛未运行、店铺离线、页面未就绪或请求超时时明确报告不可用；已有成功结果保留并标明时间及刷新失败。只有确认成功且空的结果才能显示“暂无订单”。
6. 返回有分页或截断迹象时保留 has_more 等信息，不宣称订单已经完整。首版不假设一次查询能获得买家的全部历史订单。

### 18.6 只读边界与平台隔离

现有 `order_service.py` 的订单快照处理关联签收关怀、主动话术复查等逻辑，因此不能仅把千牛快照接入现有入库函数就视为只读完成。

实施时应明确区分“订单保存/展示”和“订单自动化资格”：千牛订单首版只保存、查询和通知界面，不创建追单、关怀、复查或发送任务；现有调度器也不能把千牛订单当作新增自动化数据源。拼多多原有功能保持既有规则，需验证通用平台范围配置不会绕过隔离。

故障范围应限制到能力：千牛订单读取失败不影响千牛收发消息，也不影响拼多多订单与聊天。平台账号、会话和订单归属在后端入库时仍须校验，不能仅依赖前端传参。

## 32. 自动转接与千牛自动回复内容规则设计（2026-09-15，待实施）

本节记录已讨论确认的下一阶段方案，尚未实现或完成真实自动转接验证。第 31 节的手动转接、在线名单、业务回执和转回恢复为实施基础；本轮仅补充文档，不修改代码、不重启服务、不发送消息或执行转接。

### 32.1 范围与平台隔离

目标是在千牛无法可靠回答、客户明确要求人工，或客户明确提出定制/约稿办理意愿时，自动选择同店铺在线客服接待。固定转接提示语为“为您转接中”，替代此前讨论的“马上为您转接客服”。第一版不增加客户确认步骤，不先实现技能分组和负载分配。

复用现有机器人“需人工时转移会话”策略及自动回复、自动发送开关，但执行通过千牛独立 worker 和 transfer 服务。当前 `_transfer_conversation_enabled` 只允许拼多多，不能只放开平台判断就视为接入完成；千牛任务路由、状态管理、提示发送和转接执行都需要独立适配。拼多多原有行为保持不变。

### 32.2 触发判断与定制、约稿意图

以下情况可以进入自动转接决策：商品资料、知识库和历史不足以支持回答并命中兜底策略；AI 判断需要人工核实或处理；客户明确要求人工；客户明确要办理定制或约稿。不仅依赖模型自报置信度，应保存触发原因及对应的消息依据。图片或商品卡片本身不构成转接理由。

定制和约稿需要区分“普通咨询”与“明确办理意愿”，结合最近上下文判断，不使用关键词命中即转接的规则：

| 客户表达或上下文 | 处理方式 |
| --- | --- |
| “支持定制吗？”“约稿一般多久？”“怎么收费？” | 普通咨询，有资料依据则自动回答；没有可靠依据时走待人工策略 |
| “我要定制一个”“帮我安排约稿”“就按这张图做” | 明确办理意愿，进入自动转接 |
| 上文询问是否需要定制，客户回复“需要”“好的，开始吧” | 结合上下文识别为明确意愿，进入自动转接 |
| “不用定制”“我只是问一下” | 不因定制意图转接 |
| “这个能做吗？”且上下文不足 | 简短澄清；不能可靠回答时转人工处理 |

明确办理意愿优先于知识库命中：查到部分服务介绍不代表应继续自动处理具体方案或约稿安排。知识库用于正常解释服务，具体办理交给人工。拼多多现有“主账号定制确认提醒”属于平台特定场景，不能原样套用到千牛。

### 32.3 自动执行顺序

1. 确定需要人工后，创建带来源消息标识的处理记录并锁定本次会话流程。新消息继续入库，暂停该会话普通 AI 回复，避免同一批消息重复触发提示和转接。
2. 查询当前店铺完整客服名单及电脑端、手机端在线状态，排除主账号、当前客服、离线和状态未知账号。无候选或查询失败时标记待人工，不发送“为您转接中”。
3. 第一版按店铺在合格在线名单中轮询选择目标，记录选择结果。当前名单中的 `unreplyNum=0` 是占位值，不能作为真实接待负载或“最空闲客服”的依据。
4. 使用现有千牛发送链路发送固定提示语“为您转接中”，确认业务发送成功后才执行后续转接。发送失败或结果待确认时暂停，不盲目重发，也不把请求已投递当作发送成功。
5. 提交前再次校验会话身份、目标账号归属和在线状态。目标离线且尚未调用转接时可重新选人，不重复发送提示；已无候选则保留当前接待、标记待人工并记录原因。
6. 通过千牛独立转接服务执行 `transferContact`，沿用真实业务回执确认。成功后停止源账号该会话自动回复并取消未发出的普通回复任务；明确失败则保留接待、标记待人工，避免继续生成无依据回复。
7. 已调用但结果不明时保持 `confirmation_pending`，不自动重试，也不换另一个客服再次转接。界面显示待核对原因及目标客服。

拼多多现有“提示语发送成功后创建转接任务”的顺序可以复用，但千牛必须接入自身的身份检查、在线复查、操作记录及回执判定。业务 API 负责决策、任务依赖、幂等和审计，桌面 worker 负责查询、选择与原生平台执行；AI 不生成目标账号或底层接口参数。

### 32.4 并发、状态与转回防循环

准备转接和发送提示期间，需要暂停普通回复，但允许本次操作绑定的提示语发送。不能提前直接启用当前阻断所有发送的千牛转接屏障，否则提示语也会被拦截；提示成功且发送结束后，再进入正式转接屏障。转接流程与人工发送/手动转接必须共用会话级互斥检查。

以店铺账号、会话、来源消息和操作 ID 关联提示发送、目标选择及转接结果，重复事件不能重复发送或转接。保留决策原因、提示任务和回执、源/目标账号、状态变化和业务证据。自动转接与手动转接应共用千牛接待状态依据，避免 `auto_transfer` 仍为 `transferred` 而千牛操作已为 `returned`，造成永久抑制回复。

转回处理继续遵循第 31.6 节已实现的身份和来源验证范围，并新增以下自动策略约束：

- 有效转回通知保持平台消息身份，可以触发一次继续接待或简短接待语，但通知本身不能触发再次自动转接。
- 对刚转回、仍未解决的同一问题，不自动循环转出；没有可靠答案则标记待人工。客户明确提出新的人工请求时重新判断，不因重复通知、历史重放或同一问题追问解除防循环限制。
- 转回不能恢复原来已取消的发送任务。转回恢复与自动策略状态更新应保持一致。

### 32.5 千牛自动回复禁止内容

仅对千牛自动出站内容追加规则，不改买家原始消息、历史展示，不把新增限制扩展到拼多多或手动回复。这里的范围不代表撤销其他链路已有的公共发送校验。

以下词语本身禁止出现在最终自动回复中，包括引用客户原话、否定句、解释句和知识库原文引用：

```text
微信、v、qq、手机号、电话、加我、私聊、私下、支付宝、二维码、别的平台、网盘、非淘宝链接
```

例如“我们不支持微信联系”也不能发送，可改为“您可以直接在当前会话中沟通”。按已确认的严格包含语义，`v`、`qq` 大小写不敏感，`VIP` 及英文商品名中包含的 `v` 同样会命中，需要重新组织表达，不能直接删字符拼接成不完整回复。

“非淘宝链接”既是禁用字面词组，也涉及实际网址检查。当前公共规则已拦截各类网址，第一版继续保留，不因千牛新增规则放开淘宝网址。以后如需自动发送淘宝商品链接，再独立设计允许域名与 URL 校验，不能只凭文本包含“taobao”放行。

采用两层控制：

1. 生成前，仅为千牛请求追加平台提示词，明确上述禁止内容及正常咨询/明确办理意愿的处理规则。平台约束对知识库片段、商品资料、客户引用和兜底内容同样有效。
2. 生成后及最终自动出站前，由程序校验最终完整文本，涵盖 AI 正文、固定提示语、兜底话术及后续拼接内容。命中时原候选不可进入发送队列；提示词本身不能作为绝对保证。

首次命中后，最多尝试一次受约束改写并重新校验，不简单删除禁词。仍不通过则进入人工处理流程，有在线客服才发送“为您转接中”并按发送回执继续转接；无候选则标记待人工。改写只能调整合规表达，不能补造事实或绕过明确办理意愿的转接决策。

### 32.6 实施顺序与验证目标

1. 实现千牛独立意图规则和出站内容约束，覆盖普通咨询、明确办理、上下文确认、否定和含糊表达，以及禁词、大小写、引用、兜底和最终拼接校验。
2. 接入在线名单轮询、提示发送确认、独立转接任务和统一状态管理。复用已验证的手动底层能力，不修改拼多多协议参数或执行分支。
3. 验证无在线客服、提示发送失败/待确认、选人后离线、重复消息、并发人工操作、转接明确失败/待确认、转回后防循环和旧任务不复活。
4. 离线及模拟验证通过后，使用授权测试会话验证“普通咨询正常回复”和“明确定制/约稿 -> 为您转接中 -> 真实转接”的区别，并核对回执、消息顺序及接待状态。代码测试通过与真实平台验证分别记录。

本节方案已确认，以上自动转接串联、定制/约稿规则和千牛新增禁词校验均仍待实施。

### 33.1 已接入的决策与执行链路

- AI 服务新增 `app/qianniu_policy.py`，仅千牛先判断意图再决定是否使用 QA 直接命中。新增 `custom_order_intent`，区分普通咨询、明确办理及需澄清场景；明确的定制/约稿办理意愿进入人工流程，知识命中不能覆盖。结合最近历史解释“需要”等简短确认；额外用窄规则识别明确办理表达。涉及定制/约稿上下文时，不让已有邮件收集流程抢先处理该消息。
- 千牛基于商品资料生成回复时，使用独立 JSON 输出协议：`answerable / text / reason`。读到部分片段但仍缺少关键事实时返回需人工，而不是因为检索命中就继续发送；无效输出也不直接当正文发送。普通咨询有明确依据时生成正常回答，商品卡片可基于已知规格作简短引导。其他平台继续使用原生成协议。
- 业务 API 新增 `qianniu_auto_transfer.py`。复用机器人“转移会话给其他客服”策略，并校验全局自动回复开关、机器人在线状态、自动发送开关及店铺范围。第一轮实现中兜底转接仍遵循“兜底时标记待人工”配置；该历史行为已由第 49 节的千牛自动转接优先级规则覆盖。明确办理、人工请求及输出校验失败可进入千牛独立人工决策。
- 流程分为 `qianniu_transfer_prepare`、固定提示语 `send_message`、`qianniu_transfer_execute` 三个任务阶段。准备任务只查在线名单；无候选则不创建提示任务。收到可用目标后才创建唯一“为您转接中”提示任务；只有 `text_sent=true` 且有平台消息 ID 的成功回执，才创建执行任务。
- 桌面端 `transfer-service.js` 复用已有原生查询与转接能力，在当前 worker 生命周期内按店铺轮询在线候选。执行阶段重新查询名单，优先使用已选目标；若已离线且尚未调用，则选择其他在线候选。最终页面仍再次检查目标在线、同店铺和买家身份。不调用切店铺、切会话、输入框或 Enter。
- 成功判定继续复用 `cloudkefu.forward/3.0` 业务回执。API `transfer/begin` 增加自动任务标识校验，仅允许已完成提示发送的执行任务进入原生提交。已有成功业务记录优先于迟到的任务失败上报，避免界面将真实成功覆盖成失败。

### 33.2 统一屏障与故障处理

自动与手动转接共用 `qn-transfer:{conversation_id}` 独立操作记录；保留既有记录类型 `qianniu_manual_transfer`，通过操作内 `source=automation` 区分自动来源，不另建相互独立的接待状态。自动操作额外记录机器人、来源消息、触发原因、目标和提示任务。

新增准备阶段 `preparing / ack_queued / ready`，与原 `transferring / transferred / confirmation_pending` 一起阻止普通发送。只有绑定当前操作、正文准确为“为您转接中”的唯一提示任务，可以在 `ack_queued` 阶段发送。任务创建、派发、确认及原生发送前都进行校验；消息中心准备阶段也禁用普通发送和手动转接。

明确失败或无在线客服时，保留当前接待、标记待人工并取消未发出的旧普通回复，不自动继续回答。提示已经提交但发送结果不明时保留 `confirmation_pending`，并标记待确认的是提示发送阶段；该阶段不能被误当成已经执行过转接的操作来处理转回通知。执行中断且无法确定是否调用成功时，同样保持待确认，不自动重试。

任务派发时检查准备流程是否关闭或超过五分钟。未提交的工作取消并转待人工；提示可能已提交时保持待确认。千牛状态检查在独立事务范围内执行，检查异常时停止本轮千牛任务派发，其他平台任务仍可派发。全局数据库本身不可用不在平台隔离能力范围内。

转回继续采用第 31.6 节已有的证据和身份核对，恢复时同步旧 `auto_transfer` 展示状态。平台转回通知可以生成接待回复，但不能再次触发自动转接。第一版防循环采用保守边界：处于已转回状态的会话，只有客户新的明确人工请求才允许再次自动转出；其他需人工情况先标记待人工，尚未实现语义层面自动判断“这是另一个已解决后出现的新问题”。已取消的旧发送任务不复活。

### 33.3 千牛自动回复禁词实现

- AI 意图与正文生成请求追加千牛专用提示词，要求禁用第 32.5 节词语本身，否定句、引用和知识库答案也不例外。`v / qq` 大小写不敏感，包含 `v` 的英文词也拦截。

`qn-im-bridge-hook-server.js` 增加有界内存通知队列和只允许本机 Node 客户端读取的 `/qn-bridge/notices`。接收时以页面心跳中的 `loginID.targetId / havMainId` 为可信账号来源，校验 CID 必须属于该主账号、买家必须是 CID 的另一端、`fromId` 必须等于买家 UID、`toId` 必须等于当前客服 UID，并只接受固定事件名。队列按 `shopUid + cid + messageId` 合并重复通知，最多保留5000条；服务实例 ID 用于 bridge 重启后重置消费游标，浏览器来源不能读取队列。

worker 在原有串行轮询中先读取结构化通知，再读取 `app.log`，两条来源统一进入同一个 wake 处理器，并继续使用 `shopUid + cid + messageId` 去重。结构化通知产生的业务事件标记 `source=qianniu_bridge_notice`，诊断标记 `source=bridge_notice`；日志来源保持 `qianniu_app_log / app_log`。bridge 不可用、页面刚启动尚未注册、千牛升级导致页面模块未加载时，原有 `OnMessageArrive` 仍可触发读取。首次历史读取失败不会永久占用去重键，后到的日志事件可以再次兜底。超过60秒的积压通知只作为历史快照导入，不触发自动回复。

## 46. 千牛看图意图与邮件交付流程（2026-09-17）

千牛看图请求拆为两个独立意图。客户询问“怎么看图”“图片在哪里看”“看图链接地址”或查看入口时，判为 `image_delivery_intent=email_link_request`，跳过 QA、商品检索和图片转接，进入邮件工作流。客户要求查看某件商品的实物图、实拍图、效果图、细节图、样图或照片时，判为 `photo_request`，继续发送“为您转接中”并转接在线客服。仅讨论图片含义、询问图片与实物是否一致、客户自己发送图片或明确不要图片，不得按索图转接；语义不清时由模型澄清，不猜测。

邮件工作流先按当前千牛平台账号选择已绑定且启用的模板，再排队回复“亲，请发送一下完整邮箱号哦~”。提示发送任务排队后为 `prompt_pending`，只有千牛确认正文已发送才进入 `waiting_for_email`；提示发送失败时结束流程并标记待人工，不能假定客户已经看到提示。后续客户发送完整邮箱时，程序从当前入站文本提取地址，恢复同一工作流并使用此前固定的模板。等待状态的判断只看当前新消息，不再扫描历史中的“图”字，因此最初的“怎么看图”不会使第二轮邮箱失效。邮件收件地址加密保存，日志和任务列表只保留脱敏地址；幂等键防止同一来源消息重复发送。

只有 SMTP 任务明确返回 `sent` 后，才排队回复“亲，已发送到您的邮箱，陌生邮件可能存放垃圾邮件里，请注意查收哦~”。SMTP 失败、模板缺失、店铺绑定不匹配或结果不确定时不得发送成功话术，也不得自动跨店铺、跨平台复用模板。现有千牛违禁词规则继续禁止在聊天正文中发送网址、联系方式或外部链接；客户邮箱仅作为入站工作流槽位，不回显到聊天正文。

专项测试覆盖通用看图入口、具体实物图请求、图片与实物比较反例、QA 短路、等待邮箱状态跨历史恢复、邮箱解析、店铺模板绑定、SMTP 失败和幂等发送。当前运行数据中的邮件服务开关仍为关闭；唯一现有模板绑定的是拼多多“小源等身抱枕”账号，没有任何千牛店铺绑定模板。因此本节记录的是已实现且通过隔离测试的能力，不代表已完成真实邮件发送。上线测试前必须在管理后台启用邮件服务，并为目标千牛店铺单独建立或绑定模板；不得自动启用外发能力或借用拼多多模板。

## 47. 邮件失败转接与模板平台级联（2026-09-17）

邮件发送只有在 SMTP 任务明确返回 `sent` 时才回复成功话术，并结束邮件工作流，不触发转接。SMTP 抛出明确异常或任务终态不是 `sent` 时，工作流记录为 `failed`，结果增加 `email_send_failed` 风险标记并进入 `human_review`；不向客户发送“邮件失败”话术，也不自动重试邮件，避免不确定结果造成重复投递。

自动回复编排在普通消息发送任务创建前识别 `email_send_failed`。已启用“转移会话给其他客服”策略且会话具备可转接身份时，直接复用现有自动转接链路：先查询同店铺在线客服，有候选后只发送一次“为您转接中”，确认该提示发送成功后再执行转接。策略未启用或会话不可转接时只标记待人工；无在线目标、提示发送失败或回执不确定继续采用原有转接失败及待确认保护，不把邮件失败误记为转接成功。

管理后台邮件模板新增平台与店铺两级选择。平台目前只提供拼多多和千牛；未选择平台时店铺控件禁用，选择后只展示该平台的启用账号，切换平台会清除原店铺选择。编辑已有模板时根据绑定账号反推平台；列表以“平台 · 店铺”展示绑定关系。启用模板必须在界面中同时选择平台和店铺，停用模板仍可作为未绑定草稿保存。数据表继续只保存唯一的 `platform_account_id`，平台由账号关系确定，不新增可能与账号冲突的冗余字段。

本轮定向验证包括 SMTP 异常、非 `sent` 任务、成功邮件保持原路径，以及千牛邮件失败只创建转接准备而不创建失败回复任务；业务 API 相关 `unittest` 29 项、桌面 TypeScript 检查和差异检查通过。未启用邮件服务、未新增或复制千牛模板，也未发送真实邮件、客户消息或执行真实转接。

## 48. 移除自由文本邮件触发场景（2026-09-17）

管理后台原“需要走邮件服务的场景”会进入首轮模型提示词，并参与模型不可用时的本地子串匹配。配置中包含“定制”“资料地址”等宽泛表达时，可能在千牛专用规则之前把正常咨询或应转接的明确办理请求误导到邮件流程，因此该配置不再作为意图来源。

本轮删除后台“邮件触发策略”说明和场景输入框，只保留进入邮件流程后的收集邮箱、发送成功及缺少模板话术。业务 API 不再向 AI 传递 `email_trigger_scenarios`，AI 提示词与本地兜底均不读取或匹配该字段。数据库和 API 字段暂时保留用于旧客户端兼容，但读取恒为空、保存强制写空；历史值即使仍存在于升级前数据库中也不会影响判断，下次保存邮件配置时会被清空。

邮件入口改为仅由明确规则产生：千牛“怎么看图/看图入口”进入邮件工作流；具体商品实物图请求进入自动转接；明确办理定制或约稿进入自动转接；普通定制咨询可按知识回答。通用兜底只在客户明确提到邮箱或邮件时识别邮件意图，不能再用后台自由文本扩张范围。

## 49. 邮箱不可用与邮件流程中断（2026-09-17）

对“小源圆不圆:忘念 / tb328039366”的只读记录复核表明，首轮“怎么看图 -> 提供邮箱 -> 邮件成功”已经正常完成，随后“下单后多久发货”也正常进入商品咨询。异常从客户再次发送“没有邮箱”开始：包含“邮箱”的否定表达被重新建立为 `waiting_for_email`；紧接着“没有邮箱，怎么看图”又因确定性看图入口规则建立第二条等待流程；后续“推荐什么材料”被活动邮件工作流直接截获，没有进入模型。两条索要邮箱消息的发送任务分别出现回调超时和准入 epoch 已消费，进一步造成界面中的失败气泡，但发送失败不是错误路由的根因。

本轮把邮箱不可用提升为邮件入口之前的程序级规则。活动流程收到“没有邮箱”“无法提供电子邮箱”“邮箱号给不了”等明确拒绝或客观不可提供表达时，状态改为 `cancelled_no_email`，结果进入 `human_review`；已启用千牛自动转接时复用现有链路，只发送“为您转接中”并在确认后转接同店铺在线客服。当前消息同时包含“怎么看图”也不得重新启动邮件流程。该规则不把“没有收到邮件”识别成没有邮箱，有合法邮箱地址时仍优先提取并发送。

活动邮件流程只允许有效邮箱继续恢复。客户改问材质、商品、物流等其他问题时，旧流程改为 `cancelled_interrupted`，当前问题重新进入正常 AI、知识库和商品资料链路，不再重复索要邮箱。客户在已经收到一次索要邮箱提示后重复询问“怎么看图”，视为自助邮件路径无法继续并转接客服；含义不明确的其他表达仍可交给模型结合上下文判断，但模型不能覆盖上述高置信规则。

同一用户、会话、机器人及 `collect_email_for_link` 类型只保留最新的一条活动流程。读取时会把其他未过期活动记录收敛为 `cancelled_superseded`；新建前再次查询活动流程，降低两条入站消息并发创建重复等待记录的风险。任何切换路线都必须先明确关闭旧流程，不能再通过仅清空局部变量绕过状态迁移。

索要邮箱提示增加发送确认状态。任务排队后由 `waiting_for_email` 转为 `prompt_pending`，发送成功回执后才恢复为 `waiting_for_email`；结果待确认时保持 `prompt_confirmation_pending`；明确失败则将流程置为 `failed` 并标记 `email_prompt_send_failed` 待人工处理。迟到回执只允许更新仍处于提示发送状态的流程，不能重新激活已经取消、完成或失败的流程。

### 兜底回复的自动转接优先级

千牛机器人同时开启自动发送并将需人工策略设为 `transfer_conversation` 时，AI 返回 `workflow=fallback_reply` 就直接进入千牛自动转接准备，不再受 `fallback_mark_human_required` 开关限制，也不先发送普通兜底话术。流程仍为先查询同店在线客服，有合法目标后发送“为您转接中”，取得业务成功回执后再执行转接。

`fallback_mark_human_required` 仍用于 `mark_only` 策略和其他平台，本轮不改变拼多多的既有行为。问候、感谢等确定性短消息的直接回复不属于 `fallback_reply`，不会因此触发转接。没有在线目标、提示发送或转接结果不确定、操作冲突以及转回防循环等情况继续保留待人工或待确认状态，不盲目重试。

专项测试覆盖明确无邮箱、邮件未送达反例、合法邮箱优先、重复看图请求、等待期间转向普通商品咨询、重复活动流程收敛、提示发送失败关闭流程，以及原有千牛自动转接确认屏障。测试只验证任务编排，没有向真实客户发送消息、邮件或执行转接。

## 50. 未知消息原始证据、诊断统计与历史重投影（2026-09-18）

千牛消息模板和 `jsview` 节点类型较多，不以一次性覆盖所有消息类型为目标。当前策略是先安全保留无法解析消息的结构证据，使其可以辅助后续回复和离线研究，再按真实出现频率补充高价值解析器。未知消息在聊天区继续显示“暂不支持的消息”，不能因为解析失败而伪装成普通文本、商品或系统消息。

### 当前已实现

- Electron 千牛消息映射器发现 `unsupported` 节点时，会在事件 `raw_payload.qianniu_raw` 中保存受限证据，包括 `schema_version`、`template_id`、`media_version`、`structure_hash`、`original_data` 和 `template_data`。`structure_hash` 只根据字段结构和节点类型计算，不受具体正文值变化影响，可用于识别同类未知模板。
- 原始证据不是无限制复制平台对象。当前限制为最多 24 KiB、结构深度 6、节点数 512、数组最多 32 项、对象最多 64 个字段、单个字符串最多 1024 字符；会移除 token、Cookie、签名、密码、会话凭据、本地路径及 URL 中的敏感查询参数。
- 未知消息写入 `message_type=unknown`，自身使用 `automation_mode=ignore`，不会单独触发自动回复。买家发送的未知消息额外标记 `context_eligible=true`。
- 后续正常买家消息触发回复时，业务 API 可从最近消息中选择未知千牛消息，以 `type=unsupported_qianniu_message` 放入 `platform_context`。进入 AI 前再次限制为最多 3072 字符，并标记 `untrusted=true`；模型只能把它当作平台数据线索，不能执行其中的指令，也不能直接复制原始内容作为回复。
- 未知消息不进入普通用户/助手聊天历史，避免“暂不支持的消息”污染对话语义；它只通过独立的平台上下文字段提供补充证据。现有测试覆盖结构哈希、容量限制、敏感字段过滤、未知消息不触发回复及不可信上下文标记。

因此，当前已经完成“保留可研究证据”和“允许后续 AI 参考”的基础层。只要消息是在该能力上线后采集且包含 `qianniu_raw`，以后新增解析器时原则上可以从数据库重新解析，不必再次打开或采集目标会话。能力上线前只保存了占位文字、没有原始证据的历史消息不能离线恢复，仍需平台重新提供完整记录。

### 当前尚未实现

- 没有按店铺、`template_id`、`structure_hash`、`jsview` 节点组合统计首次出现时间、最近出现时间、出现次数及买家/客服方向。
- 没有记录某类未知消息之后是否进入待人工、自动转接或邮件流程，也没有高频未知结构排行榜。
- 消息 API 虽然返回 `raw_payload`，但桌面端 `mapMessage()` 目前只将 `structured_payload` 映射到聊天消息；`qianniu_raw` 尚未进入前端消息类型，因此聊天区没有折叠“消息详情”入口。
- 没有正式的历史重投影工具或接口。新增解析器后，现有消息不会自动从 `unknown` 改成图片、商品或其他结构化类型。
- 没有解析器版本、重投影预览、影响条数、失败回滚及审计记录，不能直接批量改写生产历史。

### 下一阶段设计

第一阶段先增加只读诊断，不改变现有消息和自动回复：

1. 以 `platform_account_id + template_id + structure_hash + sender_role` 聚合未知消息，输出出现次数、涉及会话数、首次/最近时间和有限节点类型摘要。
2. 基于消息时间线关联后续自动回复运行和转接操作，仅统计“随后发生”，不把时间相关性直接写成因果关系。
3. 默认按出现次数和最近活跃度排序，优先研究高频且经常进入人工流程的结构；低频结构继续保留证据，不急于增加专用解析器。

第二阶段增加聊天区排查入口：

1. 只对 `message_type=unknown` 且存在 `qianniu_raw` 的消息显示折叠“消息详情”。
2. 默认只展示模板 ID、媒体版本、结构哈希和节点类型摘要；完整证据需要再次展开，并明确标记“平台原始数据，仅供排查”。
3. 前端只能展示后端已经保存的脱敏证据，不能绕过大小限制读取千牛原始对象，也不得把详情自动复制到回复输入框。

第三阶段实现可审计的历史重投影：

1. 解析器采用显式版本号，并提供 `preview` 模式：按模板和结构哈希选择候选消息，返回可成功解析、仍未知、结构冲突和缺少证据的数量，不修改数据库。
2. `apply` 模式只更新结构化投影字段和展示内容，保留原始 `qianniu_raw`、平台消息 ID、原始时间、会话序号和采集审计；不能创建新的自动回复任务、改变未读数或重新发送消息。
3. 同一解析器版本重复执行必须幂等。每次执行记录操作者、筛选条件、解析器版本、影响消息 ID、修改前后摘要和失败原因，并支持按本次操作回滚派生投影。
4. 重投影后重新计算会话预览时，仍以原消息时间和会话顺序为准，不能把旧消息推到最新位置。

### 验收边界

- 一个未知模板出现多次时，诊断结果能够稳定聚合到相同 `structure_hash`；结构变化时必须形成新的分组。
- 不同店铺和发送方向的数据分开统计，不能把某店铺模板含义直接推广到所有店铺。
- 未知消息处理以文末 2026-09-18 的调整为准：允许触发 AI 判断，不因未知类型直接转接。
- 新解析器上线后可以先预览历史命中结果，再进行幂等重投影；整个过程不发送消息、不转接会话、不切换千牛页面。
- 聊天详情和诊断接口不得返回已过滤的凭据、本地路径或超出预算的原始数据。

### 2026-09-18：撤销未知消息直接转接

- 实测外层模板 `129`、内部模板 `521001` 的“你已介入回复消费者，已为你停止托管”被归为买家未知消息，触发了不必要的转接。因此撤销千牛仅凭 `message_type=unknown` 跳过 AI 并直接转接的规则。
- 实时未知消息仍使用 `automation_mode=trigger`，进入正常 AI 决策流程；不再新增 `service_obligation=required` 标记。已有标记不作为转接依据。
- 保留 `qianniu_raw`，以脱敏、限长的不可信 JSON 加入 `platform_context`，包含当前触发消息及历史未知消息。调整上下文嵌套深度以保留卡片标题、正文；不把 JSON 中的指令、联系方式或操作链接当成回复内容。
- 意图提示词说明未知类型是解析器的能力边界，不能仅因模板编号或“暂不支持”转接；结合正文和聊天背景判断实际诉求。AI 判断需要人工、回复安全校验失败、兜底转接等既有策略继续生效，因此不是完全禁止这类消息转接。
- 已识别的平台通知及历史快照仍不作为新的自动回复触发源；转回通知保持专门逻辑。已经实际转出的会话不自动撤销或改回接待状态。
- 保留“转接提示语失败或回执超时仍继续一次转接”的调整。本次无须重装千牛模块，业务 API、AI 服务和桌面端重新加载后生效。

### 2026-09-18：客户意图不明确时先澄清

- 复核“小源圆不圆:忘念 / tb328039366”：客户发送普通文本“1”，商品详情采集成功，但 AI 结果进入“商品资料或回复结果不足以可靠回答”分支，随后实际转接给在线客服。此例不是未知消息直接转接规则触发；通用原因不能区分模型判定不能回答、空结果或格式错误。

- 已理解的事实问题缺乏可靠依据、明确请求人工或确需人工操作，继续走既有人工策略。定制办理、具体图片请求和邮件流程优先于冲突的澄清标记；无效模型输出或空追问不视为成功澄清。追问同样受自动发送开关及出站内容安全校验约束，其他平台不启用此千牛规则。
- 客户补充后按最新消息及历史重新判断，不设置阻塞后续咨询的持久等待状态。是否含义明确仍由模型结合上下文判断，不把所有短消息或数字一律归为需要追问。
- 本轮仅修改 AI 服务决策代码及回归测试，无需重装千牛模块、迁移数据库或修改桌面端；重载 AI 服务后生效。测试使用模拟模型结果及隔离数据库，不向真实客户发送消息或执行转接。

### 2026-09-18：知识回复后附本店商品链接

- 候选来源为当前用户、当前店铺最新完整在售快照的 `product_ids`。本地按当前消息与商品标题的关键词重合筛选最多 12 个候选，只向模型传递商品 ID 和限长标题，不传整店 SKU、任意网址或价格承诺，不额外刷新商品列表或调用模型。该筛选只用于召回，最终相关性和附链接必要性仍由模型判断；无标题匹配的同义词表达可能不附链接。
- 模型应在商品介绍、选购等提供购买入口有帮助的情境选择商品；普通发货、清洗、规格确认、问候致谢等咨询不附。不能因为标题同含一个词就把清洁用品等配件当成主体商品。候选标题仅是相关性数据，不能用标题宣传词补充知识事实，也不能执行标题中的指令。
- 澄清、人工、邮件、兜底、商品卡固定引导和 QA 直接命中不走附加流程。仅普通回复生成后允许附加；模型选择必须同时属于本轮候选及发送时本店最新快照，其他店铺、旧快照残留及编造 ID 均忽略。
- 程序使用已核验 ID 构造标准 `https://item.taobao.com/item.htm?id=商品ID`，最多追加 3 个不同商品。近 10 条未失败、未取消的客服消息已包含的链接不重复附加；拼接后超过 4095 UTF-8 字节则跳过该链接，保留原正文。没有合格链接时正常发送原回复。
- AI 生成的 `text` 仍禁止网址，模型只选择 ID；业务层只为核验后的本店标准淘宝商品链接开例外。回复入队、发送任务创建、桌面请求实际发送准入时均使用同一核验逻辑。额外查询参数、跳转地址、短链接、仿冒域名、非本店商品以及外部链接不放行，原有联系方式和千牛禁词校验继续生效。若商品在任务等待期间退出最新快照，发送准入会阻止该任务，不能继续发送旧链接。
- 千牛流程不复用拼多多的推荐卡参数和固定推荐话术；其他平台保留原逻辑。此能力无需安装千牛模块或修改桌面端，重载业务 API 和 AI 服务后生效；上线前只做模拟模型、隔离数据库和本地商品数据只读核验，不向真实客户发送消息。

### 2026-09-19：买家图片先澄清，无人在线不阻断后续咨询

用户同意优先补齐千牛两处行为，复用现有 AI、消息发送及自动转接链路；本轮不扩展拼多多策略，也不接入图片识别。

**图片进入回复判断**

- 移除千牛纯图片在业务层直接进入 `image_message` 人工分支的处理，允许调用 AI。`qianniu_unread_image` 仅表示收到图片，明确 `vision_available=false`；不把图片 URL 作为这一上下文发送给模型，不下载图片、不推断画面或图中文字。图文混合消息也携带该提示，文字继续参与正常理解。
- AI 结合前文、文字补充和已有商品/订单/知识资料判断：能回答就回答；只有图片且诉求不明时，简短询问想咨询什么或请客户用文字说明关键内容。同一个未解决问题已经主要澄清一次，补充后仍无法理解或仍只有不可读取图片时，返回人工处理结果，按机器人设置转接。
- “同一问题已追问”由模型参考最近实际发出的对话判断，不采用整个会话的硬次数限制。客户补充后能回答、新话题或致谢，不因前面发过图片就强制转接。提示与模拟测试不代表真实模型每次必然完全遵循，后续按实际反馈调整。
- 聊天历史排除千牛未发送的排队、取消、失败、发送待确认消息；原平台已经实际发生的客服文本可以作为上下文，避免看不到上一条追问或把未发送追问当成已问过。历史图片只作为背景，不因此新增触发；既有未知卡片 JSON 策略继续保留。
- 买家“发图片给客服”与“要求客服提供图片”区分：客户索要具体商品图片、办理定制等仍遵循现有人工规则；邮件看图入口仍按既有邮件流程。自动发送开关、千牛禁词/链接检查、去重及转接中的发送屏障继续生效。

**无人在线的终止语义**

- 桌面端只有在名单查询成功且可接收目标列表为空时，返回结构化 `status=no_online_target, submitted=false`。接口失败、权限/登录/身份问题、名单结构异常及非法目标不会冒充无人在线。
- 后端仅在本次操作仍处于 `preparing` 或 `ready`、任务成功返回上述结果且尚未提交转接时记录 `unavailable`。准备阶段无人时不发送“为您转接中”；告知后执行前若名单已空，也结束本次，不再提交接口。
- `unavailable` 不新增 `human_required`、不阻断新消息。旧来源不会反复尝试；新的普通问题可正常自动回复，新的人工诉求可再次查询在线目标，之后也允许人工重新选择客服转接。结束本次时取消尚未发送的旧排队回复，不能解除屏障后又发出过期答案。
- 不清除用户独立设置的人工接管，也不自动解除历史失败标记。查询故障仍保留失败/需人工处理；已经提交、已转出或转接结果待确认不适用无人在线例外。如果告知本身仍有未决发送，保持告知待核对屏障，不把它当作未发。此限制来源于发送确认，而不是永久无人在线标记。
- 消息中心复用“暂无其他在线客服，本次未转接；新消息仍会自动处理”提示，任务回执后广播会话更新；机器人配置说明同步更新。保留原有千牛在线目标选择、转回及转接回执策略。
