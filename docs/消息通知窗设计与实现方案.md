# 消息通知窗设计与实现方案

## 1. 目标

将当前基于 Electron 系统通知的“待人工处理”提醒，升级为桌面右下角常驻消息通知窗。通知窗用于集中展示所有检测到客户新消息的会话，帮助客服持续关注未处理和已超时消息。

通知窗具备以下特征：

- 独立窗口显示在桌面右下角。
- 始终置顶，可拖动移动位置。
- 支持手动收起，收起后仍继续接收消息。
- 应用退出时关闭并清空通知数据。
- 应用启动后自动出现。
- 点击客户卡片后打开消息中心对应会话。

## 2. 展示结构

窗口从上到下分为三层：

1. 顶部标题栏：显示“消息通知”，提供拖动区域和收起按钮。
2. 消息状态栏：全部消息、未超时、已超时、AI 已回复。
3. 平台筛选栏及消息列表：全部、拼多多、抖店、快手、千牛、微信等平台。

消息卡片只展示处理所需信息：

- 平台 Logo，用于区分平台，不重复显示平台名称。
- 客户名。
- 店铺名。
- 最新一条客户消息预览。
- 当前状态或计时信息。
- 状态栏与平台栏显示对应会话数量；同一会话合并为一张卡片。

平台 Logo 使用本地资源和平台代码映射，避免远程图片加载失败造成空白。

卡片采用紧凑的两行布局：第一行依次放置客户名、店铺标签和右侧状态；第二行显示最新消息预览。客户名、店铺名和预览字号保持可读性，长文本使用省略号，避免卡片高度被撑开。数量角标统一使用红底白字；未超时秒数和“已超时”使用红色；AI 已回复使用绿色；人工已回复使用中性色。

## 3. 消息范围

通知窗展示所有客户新消息，不限制为 `awaiting_reply = true` 或 `human_required = true`。

每当业务服务或 RPA 检测到客户新消息时，通知窗创建或更新对应客户卡片。客户再次发消息时，更新消息预览、消息数量和计时起点，并将卡片重新置于未超时状态。

AI 回复失败、敏感词拦截或转人工等情况，可以继续通过会话的 `human_required` 字段展示人工处理提示，但不作为客户新消息进入通知窗的唯一条件。

## 4. 状态与计时

### 4.1 状态定义

| 状态 | 条件 | 展示 |
| --- | --- | --- |
| 全部消息 | 当前通知窗中的全部客户消息 | 所有卡片 |
| 未超时 | 客户最新消息未超过 180 秒，且尚未收到成功回复 | 实时秒数 |
| 已超时 | 客户最新消息超过 180 秒，且尚未收到成功回复 | `已超时` |
| AI 已回复 | AI 成功回复了客户最新一批消息 | `AI已回复` |

“全部消息”是筛选入口，不是独立业务状态。消息可以同时属于平台筛选和一个状态筛选。

### 4.2 计时规则

- 计时起点为客户最新消息的 `latest_customer_message_at`。
- 前端每秒刷新显示经过秒数，例如 `1s`、`5s`、`179s`。
- `180s` 仍显示 `180s`。
- 从 `181s` 开始显示“已超时”。
- 客户再次发消息时，计时重置，从 `1s` 开始。
- AI 成功回复后停止计时，进入“AI 已回复”。
- 人工成功回复后停止计时，显示“人工已回复”，保留在“全部消息”，不计入“AI 已回复”。
- 回复后客户再次发消息时，重新进入“未超时”。

建议使用客户端当前时间减去服务端消息时间计算，不在数据库中每秒写入计时结果：

```ts
const elapsedSeconds = Math.floor(
  (Date.now() - Date.parse(latestCustomerMessageAt)) / 1000,
);

const status = elapsedSeconds > 180 ? 'timeout' : 'pending';
const display = status === 'timeout'
  ? '已超时'
  : `${Math.max(1, elapsedSeconds)}s`;
```

接口时间统一输出 UTC；前端根据响应中的服务端时间计算时钟偏移。计时由时间差推导，收起、刷新或休眠恢复不会丢失经过的秒数。

## 5. 数据模型

通知窗使用独立的前端展示模型，不直接把 `human_required` 当作通知状态：

实际摘要字段包括：

- `conversation_id`、`platform_code`、`customer_name`、`shop_name`。
- `message_id`、`message_text`、`customer_message_at`：当前最新客户消息。
- `reply_kind`：`null`（未回复）、`ai`、`manual`。
- `replied_at`：确认成功的回复时间。

`message_text` 表示通知窗的最新成功消息预览，`customer_message_at` 始终表示最新客户消息时间，两者不能混用。AI 或人工回复成功后，预览更新为回复正文，但计时依据仍保留客户消息时间；客户再次发消息后覆盖预览并重新计时。

卡片唯一键使用 `conversation_id`。同一会话新消息更新原卡片，重复事件和消息补全不重复创建卡片。“未超时/已超时”由界面根据时间差计算，不写数据库。

## 6. 数据同步

复用主消息中心现有 WebSocket，不增加第二个连接或固定轮询。新增只读摘要接口：

`GET /conversations/message-notices?since=<本轮应用启动时间>`

```text
RPA / 平台 worker → 业务服务入库 → 现有 WebSocket 事件
                                          ↓
                            主消息中心合并触发摘要查询
                                          ↓ IPC
                            主进程内存快照 → 通知窗
```

- 初始连接、重连，以及 `rpa.*`、`message.*`、`conversation.*`、`automation.*` 事件触发刷新。
- 250ms 合并事件，请求串行执行；请求期间发生新事件，在完成后补刷。失败使用退避重试，并显示同步异常状态。
- 摘要独立于会话列表的首页 100 条限制，按登录用户与应用运行起点查询。
- 客户新消息不受 `awaiting_reply`、`human_required` 或 `automation_eligible` 限制，图片等需人工处理的消息也纳入。
- 只认可发送成功记录；排队、生成回复、失败和待确认均不结束计时。
- 有 AI 任务来源证据时，旧消息对应任务的延迟回执不能消除新消息的待回复状态。
- 打开会话、清除未读或待人工标记不停止通知窗计时。
- 清理消息历史、删除或重置会话时，根据服务端正式消息重新投影。
- 当前运行期间的 AI 已回复记录不按时间过期。主进程保存快照，通知窗刷新后可以恢复。
- 应用退出后内存清空；下一次启动使用新的运行起点，不把上一次运行的历史记录恢复为新通知。首次历史导入中没有可靠平台时间的旧消息也不触发通知。
- 退出登录时清空客户数据；重新登录或切换账号使用新的通知会话标识，旧请求结果不能回填到新账号。

## 7. Electron 窗口设计

建议在主进程创建独立 `BrowserWindow`：

- `alwaysOnTop: true`。
- `frame: false`，由前端绘制标题栏。
- `resizable: false`，固定初始尺寸，后续可根据内容调整。
- 使用 `setPosition` 定位到当前显示器右下角。
- 标题栏设置 `-webkit-app-region: drag`，按钮设置 `no-drag`。
- 通过 IPC 接收消息快照、窗口收起和卡片点击事件。
- 使用专用 preload，只暴露读取快照、订阅、收起及打开会话，不暴露消息发送和账号管理接口。
- 开启 `backgroundThrottling: false`，保持计时刷新；使用 `showInactive()` 展示，避免抢占输入焦点。
- 默认尺寸 360×580，收起尺寸 240×40；根据显示器工作区约束边界，显示器移除时校正位置。

窗口生命周期：

1. 应用启动后自动创建并显示；未登录时展示“等待登录”。
2. 点击收起后保留置顶标题条和待回复会话数，点击展开可恢复列表。
3. 收起状态持续接收消息，不因新消息自动展开或清空数据。
   收起后收到新客户消息时，在“消息通知”文字右上角显示 8px 红点，以 1.2 秒周期柔和明暗闪烁；展开状态不显示该红点。尊重系统减少动态效果设置，此时红点常亮。
4. 退出登录时清空数据，窗口保留为等待登录状态；应用退出时销毁窗口。
5. 再次启动重新显示空通知窗，接收本轮运行的新消息。

## 8. 交互规则

### 收起状态的新消息提醒

- 红点表示“收起后有新客户消息尚未查看”，与待回复数量独立。
- 刚收起时已有会话不触发；收起后新的客户消息触发，连续消息保持闪烁。
- AI 回复成功后仍保留红点，直到用户展开；AI 回复本身不触发红点。
- 展开即清除红点，再次收起重新判断。历史数据补载、重复消息和消息内容补全不重复提醒。
- 主进程维护提醒状态和已见客户消息 ID；通知窗刷新、连接状态变化不会丢失提醒，注销及退出清空。
- 以客户消息 ID 去重，并以客户消息时间与收起时间比较，使用服务端时钟偏移校正；消息预览更新为回复正文不会改变客户消息 ID。

本次验证：通知窗逻辑测试、TypeScript 检查、生产构建和独立 Electron 冒烟均通过。已检查收起红点截图，覆盖 AI 回复后保留、渲染进程刷新后恢复、展开清除及注销清空。此次仅修改桌面端，重启桌面 Electron 主进程后生效。

### 列表操作

- 点击状态栏切换状态筛选。
- 点击平台栏切换平台筛选。
- 点击“全部”恢复全部状态或平台。
- 点击消息卡片打开消息中心并定位到对应会话。
- 打开会话可以沿用消息中心清除待人工和待回复标记的行为，但通知窗独立计时，仅成功回复能结束等待。
- 卡片按客户最新消息时间倒序排列，最新消息始终置顶。

## 9. 与现有实现的关系

已移除原 `desktop:notify-human-required` 系统通知调用、主进程去重集合和 2.5 秒弹窗队列。新窗口使用 `message-notice:*` IPC；已有待人工业务标记保留在消息中心。

通知窗把 `platformCode` 和 `conversationId` 一起传给消息中心，由消息中心根据真实平台切换筛选并定位会话。即使会话不在消息列表前 100 条，也会按会话 ID 补载后打开。

平台标识使用仓库 `resources` 目录中的本地 SVG，并复制为通知窗渲染资源：`qianniu_logo.svg`、`pdd_logo.svg`、`doudian_logo.svg`。通知窗不依赖远程 Logo 地址。

## 10. 分阶段实现

### 阶段一：窗口和静态展示

- 创建独立通知窗。
- 完成右下角定位、置顶、拖动、收起和退出销毁。
- 实现状态栏、平台栏、消息卡片和本地平台 Logo。

### 阶段二：接入实时消息

- 从消息中心控制器生成通知窗快照。
- 接入客户新消息、回复成功、会话清理等实时事件。
- 实现同一会话更新和去重。

### 阶段三：计时和跨平台定位

- 实现每秒计时和 180 秒超时切换。
- 接入全部已支持平台。
- 点击卡片后准确切换平台并打开对应会话。

### 阶段四：验证和体验调整

- 验证应用启动、登录、断线重连、收起、退出和再次启动。
- 验证连续消息、回复后再次来消息、跨平台筛选和多显示器定位。
- 根据实际使用调整窗口尺寸、卡片排序和收起后的未读提示。

### 已完成的第一版优化

- 按参考图调整为紧凑卡片布局，客户名和店铺名同一行展示。
- 店铺名使用带颜色背景的标签，状态和计时信息固定在右侧。
- 红点、未超时计时、已超时状态统一采用醒目的红色。
- 使用千牛、拼多多、抖店本地 SVG Logo。
- 后端通知摘要区分最新客户消息时间和最新成功消息预览。
- AI 回复成功后立即更新预览；发送中、失败、待确认不会提前结束计时。
- 人工回复显示“人工已回复”，不归入“AI 已回复”。

## 11. 验收标准

- 客户发来新消息后，通知窗能显示对应客户、店铺和最新消息预览。
- 未超时卡片能显示 `1s` 到 `180s` 的实时增长计时。
- 超过 180 秒后显示“已超时”。
- AI 成功回复后进入“AI 已回复”；人工成功回复显示“人工已回复”，计时均停止。
- 客户再次发消息后重新进入未超时并从 1 秒计时。
- 状态栏和平台栏筛选结果正确。
- 通知窗可拖动、置顶和手动收起。
- 点击卡片能打开正确平台的正确会话。
- 应用退出后通知数据清空，重新启动显示空窗口并接收本轮新消息，不恢复上一轮通知。
