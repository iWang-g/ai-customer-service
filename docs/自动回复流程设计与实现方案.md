# 自动回复流程设计与实现方案

## 1. 文档信息

- 项目：`D:\project-electron\ai-customer-service`
- 文档性质：自动回复后续设计与落地方案，不代表所有能力均已实现
- 编写日期：2026-07-30
- 相关文档：`docs/知识库与AI服务架构方案.md`
- 旧项目参考：`D:\ai-customer-service`

本文以当前新项目代码为准，结合旧项目已经实现的 QA 短路、两轮大模型、文档知识检索、邮件意图路由和 SMTP 邮件服务，定义新项目自动回复闭环。当前阶段仍采用本地优先策略，先保证基础链路可以运行和验收，后续再考虑云端部署、消息队列和更完整的生产治理。

## 2. 目标与原则

自动回复的目标不是把所有消息直接交给大模型，而是按成本、确定性和风险逐级处理：

1. 优先使用 QA 问答知识库的确定性答案，命中后不调用大模型。
2. QA 未命中或机器人未关联 QA 库时，才调用第一轮大模型识别意图。
3. 普通咨询只检索机器人关联的产品文档知识库，不检索图片资产。
4. 需要自然语言生成时，第二轮大模型结合上下文、意图、文档片段和机器人风格生成回复。
5. 外链、地址和资料发送进入邮件工作流，AI 只识别意图和选择动作，程序负责真正发送邮件。
6. 所有平台回复最终统一交给现有 RPA 服务执行。
7. 测试回复与真实回复共用决策链路，但测试模式禁止创建 RPA 和邮件发送任务。

核心边界：

- `business-api` 负责机器人选择、工作流状态、动作编排、任务创建和审计。
- `ai-reply` 负责 QA 策略编排、结构化意图识别、知识库调用、Prompt 组装和回复生成。
- `knowledge-base` 负责 QA 匹配和产品文档检索。
- `email-service` 负责邮件配置、模板和真实 SMTP 发送。
- `RPA` 只执行平台会话切换、文本发送和图片发送，不参与业务判断。

## 3. 当前实现基线

当前已经具备：

- RPA 客户消息入站、会话和消息持久化。
- 按平台与店铺范围选择已上线机器人。
- 机器人与多个 QA 库、多个产品库、一个语气库的真实关系。
- QA 问题精确匹配、关键词包含匹配、权重优先级、启用状态和调用次数。
- QA 命中后返回答案和可选图片。
- 产品文档导入、切片和基础关键词检索。
- DeepSeek 兼容模型调用。
- RPA 文本发送及“文本成功后发送图片”的有序任务。
- 多轮机器人测试回复界面。

当前自动回复仍是简化实现，但阶段 A 已完成主链路修正：

- `business-api` 已按机器人 `context_length` 读取最近 N 条双方消息，真实回复和测试回复共用同一裁剪规则。
- 最近消息已经传给 `ai-reply`，且当前生成 Prompt 已包含按时间正序排列的最近对话。
- 阶段 B 已实现第一轮 DeepSeek 结构化意图识别；模型不可用或 JSON 不合法时使用本地保守规则兜底。
- 普通咨询已形成“第一轮意图识别、产品文档检索、第二轮回复生成”的两轮模型链路。
- 邮件配置、邮件模板、会话级邮件工作流、邮件发送幂等记录和自动邮件动作已经具备基础实现。
- 管理后台“通用设置”自动回复总开关、机器人在线状态和机器人 `allow_auto_send` 共同影响自动回复。
- QA 命中会在本地意图分类、产品文档检索和模型调用前直接返回；QA 状态区分 `hit`、`miss`、`unavailable` 和 `skipped`。

## 4. 总体流程

```text
RPA 读取客户新消息
  -> business-api 幂等入库
  -> 检查管理后台通用设置自动回复总开关
  -> 按平台和店铺选择在线机器人
  -> 检查机器人自动回复开关
  -> 按机器人 context_length 获取最近 N 条双方消息
  -> QA 关键词策略
       命中：直接采用答案和可选图片，不调用大模型
       未命中或未关联 QA 库：进入意图识别
  -> 第一轮大模型：结构化意图识别
  -> Workflow / Action Plan 编排
       普通咨询：产品文档检索
       邮件资料：补齐模板和邮箱槽位，或执行邮件动作
       无需回复：结束
       人工处理：记录状态，暂不自动转接
  -> 第二轮大模型：生成普通咨询或追问回复
  -> business-api 创建 RPA 发送任务
  -> RPA 切换平台、店铺和会话
  -> 发送文本，必要时再发送 QA 图片
```

## 5. 入站、幂等与机器人选择

### 5.1 触发条件

只有满足以下条件才进入真实自动回复：

```text
管理后台通用设置：自动回复总开关=true
+ 入站事件是客户新消息
+ 当前平台店铺存在匹配机器人
+ 机器人 status=online 且 enabled=true
+ 机器人 allow_auto_send=true
```

测试回复不要求机器人在线，也不检查平台店铺范围，但必须校验机器人属于当前用户。

### 5.2 机器人选择

机器人匹配顺序：

1. 当前用户拥有的机器人。
2. 已上线且启用。
3. 平台范围匹配。
4. 店铺范围为全部店铺或当前平台账号。
5. 如果多个机器人覆盖同一范围，后续应显式禁止冲突或定义优先级，不能长期依赖更新时间隐式选择。

### 5.3 会话级串行

同一会话内自动回复必须串行：

- 新消息到达时生成唯一处理事件。
- 同一条入站消息只能决策一次。
- 上一条回复尚未完成时，后续消息进入等待或合并窗口。
- 人工客服接管后暂停机器人。
- 超时回复不得在客户话题已经变化后继续发送。

## 6. 上下文读取

机器人基础配置中的 `context_length` 表示读取最近多少条消息，包含客户和客服双方消息，不是“对话轮数”。

建议规则：

- 默认 20 条，允许范围 1 到 100。
- 从数据库按时间倒序取 N 条，再恢复为正序。
- 客户消息映射为 `user`，客服、机器人消息映射为 `assistant`。
- QA 匹配只使用最新一条客户文本。
- 第一轮意图识别使用最近 N 条消息并突出最新客户消息。
- 第二轮回复生成同样使用最近 N 条消息，但应避免重复追加最新消息。
- 邮箱槽位、此前追问和邮件完成提示也从会话工作流状态读取，不应只靠聊天文本猜测。

请求示例：

```json
{
  "message": "xxx@example.com",
  "conversation": [
    {"role": "user", "content": "有没有看图地址"},
    {"role": "assistant", "content": "亲，麻烦提供一下邮箱哦~"},
    {"role": "user", "content": "xxx@example.com"}
  ]
}
```

## 7. 第一阶段：QA 关键词策略

### 7.1 触发范围

仅查询当前机器人关联且已启用的 QA 问答知识库。机器人未关联 QA 库时直接跳过，不应查询全局 QA 库。

### 7.2 匹配顺序

1. 过滤未启用的问答库和问答项。
2. 按权重从高到低排序。
3. 使用最新客户消息与“问题”规范化后精确匹配。
4. 精确未命中时，判断客户消息是否包含任意一个关键词。
5. 分类只作为用户备注，不参与匹配。
6. 命中后调用次数加一。

### 7.3 命中后的动作

```text
QA 文本命中
  -> 直接采用答案
  -> 不调用意图模型
  -> 不检索产品文档
  -> 不调用生成模型

QA 文本+图片命中
  -> 先创建文本发送任务
  -> 文本成功后创建图片发送任务
```

QA 答案在发送前仍需经过基础安全检查，例如空答案、禁用条目、非法资源 URL 和平台发送限制。确定性 QA 命中不应因为普通风险关键词而自动改写答案；如果存在禁止词或高风险策略，应按机器人策略转人工或使用固定兜底，而不是再让模型自由改写。

## 8. 第二阶段：第一轮大模型意图识别

### 8.1 调用条件

满足任一条件进入意图识别：

- 机器人没有关联 QA 问答知识库。
- 已关联 QA 库但没有匹配项。
- 最新消息不是可用于 QA 匹配的普通文本。

### 8.2 第一轮职责

第一轮模型只能路由，不能生成最终客服回复。建议使用：

- `temperature=0`。
- 较低 `max_tokens`。
- JSON 结构化输出。
- 8 到 15 秒超时。
- 模型失败时使用有限的本地规则兜底或转人工。

输入包括：

- 最新客户消息。
- 最近 N 条双方消息。
- 平台、店铺和机器人信息。
- 当前邮件工作流状态。
- 邮件模板元数据：模板 ID、名称、场景、别名。
- 合规策略，例如平台聊天禁止直接发送外链。

不应提供给意图模型：

- 邮件模板中的真实外链和完整正文。
- SMTP 授权码。
- 平台 Cookie、Token。
- 无关的完整历史聊天。

### 8.3 意图协议

首期建议支持：

- `normal_question`：普通问题，需要或可选文档检索。
- `email_link_request`：索要外链、看图地址、下载地址、群链接或资料。
- `no_reply_needed`：无需继续回复。
- `human_handoff`：需要人工处理。
- `unknown`：无法可靠判断。

当前阶段不做图片资产分析和图片知识库检索。客户说“发张图看看”时，可以由文档知识和模型解释，但除 QA 条目已经绑定图片外，不自动检索或发送图片素材。

建议响应：

```json
{
  "intent": "email_link_request",
  "confidence": 0.9,
  "need_customer_reply": true,
  "need_doc_search": false,
  "need_email": true,
  "workflow": "collect_email_for_link",
  "template_id": "store-view-link-001",
  "email": "",
  "missing_slots": ["email"],
  "next_action": "ask_email",
  "risk_flags": ["direct_external_link_blocked"],
  "business_object": "王刚小店",
  "reason": "客户索要店铺看图地址"
}
```

程序必须对模型输出进行 Schema 校验。非法枚举、缺少必需字段、低置信度或解析失败不能直接执行外部动作。

## 9. Workflow 与 Action Plan

意图结果必须先转成程序可执行的 Action Plan，不能让 AI 直接调用 RPA 或邮件服务。

```text
normal_question
  -> search_product_documents
  -> generate_reply
  -> send_platform_text

email_link_request + missing template
  -> ask_template
  -> save pending workflow

email_link_request + missing email
  -> ask_email
  -> save pending workflow

email_link_request + template + email
  -> validate_email_action
  -> send_email
  -> send success/failure notice

no_reply_needed
  -> finish without reply

human_handoff / low confidence
  -> mark needs_human
  -> 暂不执行平台自动转接
```

Action Plan 建议至少包含：

```json
{
  "workflow": "collect_email_for_link",
  "next_action": "ask_email",
  "generate_reply": false,
  "need_doc_search": false,
  "email_service_required": false,
  "required_actions": ["save_pending_workflow", "send_fixed_prompt"],
  "blocked_actions": ["send_external_link_in_chat"]
}
```

## 10. 产品文档知识库检索

### 10.1 检索范围

- 只检索当前机器人关联的产品知识库。
- 不查询 QA 库、语气库或图片资产。
- 没有关联产品库时跳过检索，模型可基于上下文生成有限回复，或者按机器人兜底策略处理。

### 10.2 检索 Query

默认以最新客户消息为主。对于“可以”“好的”“那这个呢”等短确认，需要结合最近上下文构造 Query，避免用无意义短词检索。

检索结果建议返回：

```json
{
  "results": [
    {
      "document_id": "doc-001",
      "chunk_id": "chunk-003",
      "source_title": "售后说明",
      "snippet": "商品签收后七天内支持退换……",
      "score": 0.83
    }
  ],
  "trace_id": "search-..."
}
```

首期保留当前关键词检索，后续可替换向量或混合检索，但 `ai-reply` 不直接依赖知识库内部实现。

## 11. 第三阶段：第二轮大模型生成回复

第二轮仅在需要自然语言回复时调用。输入包括：

- 机器人基础风格、回答长度、称呼、上下文长度和高级指令。
- 语气知识库中的虚拟人设。
- 最近 N 条双方消息。
- 第一轮结构化意图。
- Action Plan。
- 产品文档检索片段。
- 最新客户消息。
- 平台与店铺上下文。

Prompt 的硬性规则：

- 优先回答最新客户问题。
- 历史聊天只作辅助，不重复回答已经处理的问题。
- 不编造知识片段中不存在的事实。
- 不在平台聊天中输出被禁止的外链。
- 没有程序动作结果时，不得声称邮件已发送。
- 没有 QA 绑定图片时，不得声称已经附图。
- 输出可直接发送的纯文本，不输出分析过程。

建议返回：

```json
{
  "decision": "auto_send",
  "text": "亲，这款商品通常会在付款后 24 小时内发出哦。",
  "media": [],
  "intent": {"intent": "normal_question"},
  "confidence": 0.86,
  "risk_flags": [],
  "provider": "deepseek",
  "trace_id": "reply-..."
}
```

## 12. 邮件服务设计

### 12.1 页面与配置

管理后台左侧导航新增“邮件服务”，建议包含：

- 启用邮件服务。
- 邮件服务商：QQ 邮箱、Gmail、自定义 SMTP。
- 发件邮箱。
- SMTP Host、端口、安全方式：SSL 或 STARTTLS。
- SMTP 授权码或应用密码，保存后仅返回掩码。
- 保存配置。
- 测试收件邮箱和测试发送。
- 邮件模板列表和增删改。

模板字段建议：

- 模板 ID。
- 模板名称。
- 业务场景。
- 识别别名。
- 邮件主题。
- 邮件正文。
- 启用状态。
- 可选适用机器人、平台或店铺范围，首期也可以仅做全局模板。

### 12.2 邮件服务边界

建议将邮件能力作为独立服务或独立模块，通过稳定接口访问：

```text
GET    /api/v1/email/config
PUT    /api/v1/email/config
POST   /api/v1/email/test

GET    /api/v1/email/templates
POST   /api/v1/email/templates
PATCH  /api/v1/email/templates/{id}
DELETE /api/v1/email/templates/{id}

POST   /api/v1/email/send
```

可以迁移旧项目 `python/service/email_service.py` 的以下能力：

- QQ 邮箱、Gmail 和自定义 SMTP 默认参数。
- SSL、STARTTLS。
- SMTP 登录和发送。
- 邮件地址格式校验。
- 配置、授权码和地址脱敏。
- 模板 CRUD、模板启用状态和别名。
- 测试发送。
- 认证失败、连接失败、超时和发送失败分类。
- `trace_id`、`conversation_id`、`template_id` 和 `message_id` 日志。

旧项目文件存储方式只适合作为迁移参考。新项目仍应通过 `business-api` 或独立邮件服务按用户、租户保存配置，不能让桌面端直接读取本地授权码文件。

## 13. 邮件工作流状态

### 13.1 为什么需要持久化状态

客户通常分两轮提供信息：

```text
客户：有没有王刚小店的看图地址？
机器人：亲，麻烦提供一下邮箱哦~
客户：xxx@example.com
```

最后一条消息只有邮箱，无法独立说明客户想要哪份资料。因此不能只依赖最新消息或让模型每次猜测，必须保存会话级待处理状态。

建议表：

```text
conversation_workflows
  id
  user_id
  conversation_id
  robot_id
  workflow_type
  status
  intent
  template_id
  collected_slots_json
  missing_slots_json
  source_message_id
  expires_at
  completed_at
  created_at
  updated_at
```

状态示例：

```json
{
  "workflow_type": "email_link_request",
  "status": "waiting_for_email",
  "template_id": "wanggang-shop-view-link",
  "collected_slots": {"business_object": "王刚小店"},
  "missing_slots": ["email"]
}
```

### 13.2 状态流转

```text
none
  -> waiting_for_template
  -> waiting_for_email
  -> ready_to_send
  -> sending
  -> completed

异常：
  -> failed
  -> expired
  -> cancelled
  -> needs_human
```

每个会话同时只允许一个活动邮件工作流。客户明确取消、人工接管、邮件完成或状态过期后必须关闭工作流。

### 13.3 邮箱提取与校验

- 从最新消息和当前活动工作流上下文中提取邮箱。
- 使用确定性正则提取，AI 输出仅作为候选。
- 程序再次校验格式。
- 日志只记录掩码或字符数，不记录完整邮箱。
- 没有合法邮箱时禁止调用邮件服务。

## 14. 邮件动作执行

典型流程一：缺少邮箱。

```text
客户：发我王刚小店的看图地址
  -> intent=email_link_request
  -> template_id=wanggang-shop-view-link
  -> missing_slots=[email]
  -> 保存 waiting_for_email
  -> RPA 发送固定话术：
     “亲，平台不方便直接发地址，麻烦您提供一下邮箱，我这边发到邮箱里哦~”
```

典型流程二：客户提供邮箱。

```text
客户：xxx@example.com
  -> 命中活动 waiting_for_email 工作流
  -> 提取并校验邮箱
  -> 校验邮件配置和 template_id
  -> POST /api/v1/email/send
```

邮件服务成功后：

```text
更新工作流为 completed
  -> RPA 发送：
     “亲，资料已发送到您的邮箱，请注意查收哦~”
```

邮件服务失败后：

```text
更新工作流为 failed 或可重试
  -> 不得回复“已发送”
  -> RPA 发送：
     “亲，邮件发送暂时异常，我这边帮您进一步处理。”
  -> 可标记人工处理
```

程序侧硬性保护：

- 邮件服务未启用不能发送。
- 发件配置不完整不能发送。
- 收件邮箱不合法不能发送。
- 模板缺失、停用或不适用不能发送。
- 同一动作必须有幂等键，避免重复发送邮件。
- AI 无权绕过 Action Plan 直接调用邮件服务。
- 邮件成功提示只能在服务真实返回成功后发送。
- 平台回复不得包含邮件模板中的真实 URL。

## 15. RPA 回复执行

所有平台消息仍走当前统一任务：

```text
business-api 创建 RPA task
  -> 本机 agent 轮询
  -> Electron 工作区找到平台账号
  -> 切换目标客户会话
  -> 输入并真实发送
  -> 回传完成或失败
```

回复片段：

```json
[
  {"type": "text", "content": "QA 答案"},
  {"type": "image", "url": "http://127.0.0.1:8010/api/v1/qa-assets/..."}
]
```

规则：

- 文本先发送，成功后再发图片。
- 图片失败不重复发送文本。
- 邮件动作与平台提示是两个独立动作，只有邮件成功后才创建成功提示任务。
- 同一会话的发送任务串行。
- 平台登录失效、切换失败、输入框异常和发送失败都应记录具体阶段。

## 16. 测试回复模式

机器人测试回复应与真实回复共用：

- QA 匹配。
- 第一轮意图路由。
- 产品文档检索。
- 第二轮回复生成。
- 机器人上下文长度和风格配置。

测试模式必须强制：

- `allow_auto_send=false`。
- 不写入正式会话消息。
- 不创建 RPA 任务。
- 不真正发送邮件。
- 邮件工作流只展示模拟动作，例如“将询问邮箱”或“条件满足后将发送模板 X”。
- QA 图片只在测试窗口显示缩略图和预览。

为了排查效果，测试窗口后续可增加可折叠调试信息：

- QA 是否命中、匹配类型和条目 ID。
- 第一轮意图及置信度。
- Action Plan。
- 文档检索片段。
- 模型和 token 用量。
- trace ID。

## 19. 失败策略与安全

### 19.1 模型失败

- QA 命中不受模型服务故障影响。
- 第一轮意图模型失败时，仅允许有限本地规则兜底。
- 邮箱和外链等敏感动作不能在低置信度下自动执行。
- 第二轮模型失败时使用机器人固定兜底或转人工。

### 19.2 知识库失败

- QA 服务不可用时记录 `qa_unavailable`，不能误判为确定性未命中。
- 产品检索失败时可使用无检索回复或固定兜底，取决于机器人策略。
- 不把检索服务错误内容发给客户。

### 19.3 隐私与密钥

- API Key、SMTP 授权码、Cookie 不进入前端日志。
- 邮箱只在必要动作中使用，日志必须脱敏。
- Prompt 中如确有必要出现邮箱，应使用掩码。
- 邮件模板中的真实 URL 不提供给意图模型。

## 20. 可观测性

## 21. 分阶段落地顺序

### 阶段 A：修正当前主链路

1. 修复真实自动发送分支问题并补测试。
2. 使用机器人 `context_length` 读取最近 N 条消息。
3. 确保上下文同时用于真实回复和测试回复。
4. QA 判断明确短路模型调用。
5. 增加 QA 命中、未命中和不可用状态日志。

验收：QA 命中时 DeepSeek 调用次数为零，文本和可选图片可由 RPA 正常发送。

实现状态：已于 2026-07-30 完成代码落地和自动化校验。

- 修复真实自动发送分支引用未定义 `payload` 的问题，发送前统一校验服务开关、请求开关和机器人开关。
- `context_length` 默认 20，运行时限制为 1 至 100；真实回复和测试回复都会保留最新客户消息且总上下文不超过该值。
- 生成 Prompt 已包含平台、店铺、客户、最近双方对话、最新客户问题和文档知识片段。
- QA 命中使用 `provider=qa-rule` 直接返回，不执行本地意图分类、产品检索和大模型生成；粗粒度风险关键词只记录，不改写或阻断确定性 QA 答案。
- `business-api` 记录上下文条数、机器人、发送开关、QA 状态、决策、Provider 和 RPA 任务数；`ai-reply` 记录 QA 命中、未命中、跳过、不可用以及是否模型短路。
- 新增单元测试覆盖上下文边界和顺序、三层自动发送开关、QA 模型短路、QA 不可用状态及 Prompt 去重。

阶段 A 的自动化测试已经验证 QA 命中时文档检索和 `generate_with_provider` 均为零次调用。真实拼多多文本/图片发送沿用此前已实现的有序 RPA 任务，仍建议在管理后台通用设置开启自动回复总开关后完成一次真实店铺端到端验收。

### 阶段 B：两轮大模型

1. 定义 `IntentDecision` 和 `ActionPlan` Schema。
2. 实现第一轮结构化意图模型。
3. 仅对普通咨询检索产品文档知识库。
4. 第二轮生成使用上下文、意图、检索片段和机器人风格。
5. 测试回复展示意图、检索和最终回复。

验收：普通问题先完成结构化意图识别，再检索文档并生成回复；QA 命中仍不调用模型。

实现状态：已于 2026-07-30 完成代码落地和自动化校验。

- 新增强类型 `IntentDecision`，首期意图为 `normal_question`、`email_link_request`、`no_reply_needed`、`human_handoff` 和 `unknown`；QA 命中使用内部 `qa_match` 意图。
- 第一轮调用 DeepSeek 时固定 `temperature=0` 并启用 JSON Object 输出，程序负责 JSON 提取、枚举和字段校验；无 API Key、调用失败或响应不合法时进入本地保守规则。
- 新增强类型 `ActionPlan`。模型只提供意图，程序根据意图和机器人关系生成允许动作与禁止动作，模型不能直接创建 RPA 或邮件任务。
- 只有 `normal_question` 会检索机器人关联的产品文档知识库；未关联产品库时跳过检索，仍可结合对话上下文生成有限回复。
- 第二轮 Prompt 已包含平台、店铺、客户、最近双方对话、结构化意图、Action Plan、产品文档片段，以及机器人基础风格、回答长度、称呼、自称和语气知识库虚拟人设。
- `ai-reply` 对 `email_link_request` 只返回 `defer_email_workflow` 计划和可选模板建议，明确禁止直接在平台发送外链或虚构邮件已发送；真实邮件工作流由 `business-api` 在阶段 D 编排。
- 回复响应新增 `action_plan`、`model_calls`、`qa_match` 和 `retrieval`。管理后台“测试回复”弹窗可展开查看意图、置信度、下一动作、两轮 Provider、检索数量、片段摘要和 Trace ID。
- 日志新增意图、置信度、第一/第二轮 Provider、Action Plan 下一动作、检索数量和最终决策，不记录 API Key 或完整 Prompt。

阶段 B 自动化测试已验证：QA 命中为零次模型调用；普通咨询为两次模型调用且仅在意图为普通咨询时检索产品文档；邮件意图和无需回复只调用第一轮；第一轮解析失败可以安全降级；DeepSeek 第一轮请求确实携带 JSON 模式和零温度配置。

### 阶段 C：邮件服务基础能力

1. 管理后台新增邮件服务页面。
2. 迁移 SMTP 配置、授权码、SSL/STARTTLS 和测试发送。
3. 实现邮件模板 CRUD。
4. 增加配置脱敏、错误分类和日志。

验收：用户能配置 QQ 邮箱或自定义 SMTP，并向测试邮箱成功发送模板邮件。

实现状态：已于 2026-07-30 完成基础能力代码落地和自动化校验。

- `business-api` 新增用户级 `email_provider_configs` 和 `email_templates` 正式关系表，本地 SQLite 启动时可自动创建兼容表和索引。
- SMTP 配置支持 QQ 邮箱、Gmail 和自定义 SMTP，安全方式支持 SSL、STARTTLS 和无加密模式；服务商切换时管理后台会带出默认 Host、端口和安全方式。
- SMTP 授权码或应用密码使用由服务端 `JWT_SECRET_KEY` 派生的 Fernet 密钥加密入库，读取接口只返回 `auth_code_saved`，不会把明文或密文返回前端；留空保存会保留已有授权码。
- 新增 `GET/PUT /api/v1/email/config`、`POST /api/v1/email/test` 以及邮件模板列表、创建、修改、删除接口。
- 测试邮件由用户在管理后台显式触发，可选择已启用的邮件模板或默认测试正文，并包含独立 `message_id`；认证失败、连接失败、超时和 SMTP 发送失败会返回不同错误信息，日志中的发件人与收件人地址均脱敏。
- 邮件模板保存模板 ID、名称、业务场景、识别别名、主题、正文和启用状态，目前按用户全局管理，为阶段 D 的意图路由和会话工作流提供元数据。
- 管理后台左侧新增“邮件服务”页面，支持启用开关、SMTP 配置、授权码保存状态、测试收件邮箱、测试发送和模板增删改。
- 对外显式 `POST /api/v1/email/send` 暂未开放；阶段 D 已在 `business-api` 内部接入模板邮件发送、会话工作流和自动邮件动作。

自动化测试已经覆盖：三类服务商默认参数、授权码加密回环与密文落库、留空保留授权码、邮箱日志脱敏、未启用配置保护、SMTP 认证错误分类、用户级模板 CRUD，以及新 SQLite 数据库正式建表。

真实 SMTP 发送需要用户在“邮件服务”页面填写自己的发件邮箱和授权码后，向有权接收的测试邮箱显式点击“发送测试邮件”完成外部验收；自动化测试不会擅自发送真实邮件。

### 阶段 D：邮件工作流闭环

1. 新增会话工作流持久化。
2. 意图模型读取邮件模板元数据。
3. 实现缺模板、缺邮箱的槽位追问。
4. 提取并校验客户邮箱。
5. 实现邮件动作幂等和真实发送。
6. 邮件成功后才创建“请查收”RPA 任务。
7. 测试沙盒只模拟邮件动作。

验收：客户索要资料、机器人询问邮箱、客户提供邮箱、系统发送模板邮件并在平台提示查收，完整流程可跨多轮消息恢复。

实现状态：已于 2026-07-30 完成基础闭环代码落地和自动化校验。

- `business-api` 新增 `conversation_workflows` 和 `email_send_tasks` 正式关系表，本地 SQLite 启动时会自动创建兼容表和索引。
- `conversation_workflows` 保存会话、机器人、邮件模板、已收集槽位、缺失槽位、来源消息、过期时间和完成时间，用于跨多轮恢复“等待邮箱”等状态。
- `email_send_tasks` 保存模板、来源消息、幂等键、收件人加密值、脱敏邮箱、发送状态、错误码、错误信息和 Provider 消息 ID；同一工作流、模板和来源消息只会发送一次邮件。
- 邮箱提取使用确定性正则并统一转小写；日志和发送任务只暴露脱敏邮箱，真实收件邮箱加密入库。
- `ai-reply` 的意图模型请求已接收邮件模板元数据，但仅包含模板 ID、模板 Key、名称、场景和别名，不传模板正文、真实 URL、SMTP 授权码或任何平台凭证。
- 第一轮模型可返回 `template_id` 或 `template_key` 作为模板建议；程序会校验该建议必须来自可用模板元数据，非法或编造的模板标识会被清空。
- `business-api` 在真实自动回复链路中优先恢复活动邮件工作流；如果客户上一轮已被询问邮箱，下一条只发邮箱也可以恢复此前模板并继续发送。
- 当模板缺失时固定回复“亲，请问您需要哪一份资料呢？”，当邮箱缺失时固定回复“亲，麻烦提供一下邮箱哦~”。
- 模板和邮箱齐全后才调用 SMTP；只有 SMTP 明确成功后，才创建“亲，资料已发送到您的邮箱，请注意查收哦~”这类平台 RPA 文本任务。
- SMTP 认证、连接、超时或发送失败时，工作流会标记失败，并只创建失败提示，不会回复“已发送”。
- 真实自动邮件动作受两层业务开关保护：管理后台通用设置自动回复总开关和机器人 `allow_auto_send` 均满足时才会持久化工作流、发送邮件和创建 RPA 任务。
- 测试回复和非自动发送预览只返回沙盒动作，例如 `simulate_save_pending_workflow`、`simulate_send_email`，不会创建 RPA 任务、不会写正式工作流、不会真实发送 SMTP。

当前保留的后续工作：

- 邮件发送任务还没有独立重试队列和人工重试入口。
- 每个会话同时只按“最新活动邮件工作流”恢复，后续需要显式处理多工作流冲突和客户取消语义。
- 对外 `POST /api/v1/email/send` 暂未开放，目前自动邮件发送只作为 `business-api` 内部动作。
- 真实拼多多端到端验收仍需用户配置可用 SMTP 后，在店铺会话中发起“索要资料 -> 提供邮箱 -> 收到邮件 -> 平台提示查收”的完整测试。

### 阶段 E：稳定性和云端演进

1. 会话级任务锁和消息合并窗口。
2. 自动回复运行记录和管理后台排查页。
3. 邮件、模型和 RPA 失败重试策略。
4. 人工接管暂停机制。
5. 将 business-api、knowledge-base、ai-reply、email-service 迁移到 Linux 云端。

## 22. 验收场景

### 22.1 QA 精确命中

- 客户消息精确等于 QA 问题。
- 采用最高权重答案。
- 不调用第一轮和第二轮模型。
- 调用次数增加。
- RPA 成功发送文本。

### 22.2 QA 关键词命中并带图片

- 精确未命中，任一关键词命中。
- 先发送答案文本。
- 文本成功后发送绑定图片。
- 图片失败不重复发送文本。

### 22.3 普通咨询

- QA 未命中。
- 第一轮输出 `normal_question`。
- 只检索机器人关联的产品文档库。
- 第二轮结合最近 N 条消息和召回片段生成回复。
- RPA 发送文本。

### 22.4 邮件资料请求

- 第一轮输出 `email_link_request`。
- 缺邮箱时保存工作流并询问邮箱。
- 客户下一条只发送邮箱仍能恢复此前模板。
- 邮件真实成功后才提示查收。
- 失败时不出现“已发送”承诺。

### 22.5 测试回复

- 多轮上下文与真实链路一致。
- QA 文本和图片正常展示。
- 普通咨询显示生成回复。
- 邮件场景显示将执行的 Action Plan，但不真实发邮件、不创建 RPA 任务。

## 23. 结论

新项目自动回复应采用“确定性规则优先、两轮模型分工、程序动作兜底”的架构：

```text
QA 短路
  -> 第一轮模型识别意图
  -> Action Plan
  -> 产品文档检索或邮件工作流
  -> 第二轮模型生成普通回复
  -> business-api 创建动作任务
  -> RPA 或邮件服务真实执行
```

旧项目中最值得迁移的是 QA 短路顺序、结构化意图路由、最近上下文处理、邮件模板元数据路由、邮箱槽位工作流、SMTP 错误分类和“成功后才能承诺已发送”的执行保护。新项目不直接复制旧项目的 Qt 和本地文件存储结构，而是将这些业务规则迁移到当前独立服务和正式关系模型中。
