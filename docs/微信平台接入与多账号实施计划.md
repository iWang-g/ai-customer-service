# 个人微信平台接入与多账号实施计划

> 讨论日期：2026-08-08
>
> 本文同时记录实施计划、阶段性实现和验证状态；未标记为已验证的项目仍需在真实 Windows 微信环境确认。

## 1. 背景与目标

当前项目的聚合平台主链路已经接入拼多多，下一阶段计划接入个人微信。微信的桌面自动化流程与拼多多不同，但旧项目 `D:\ai-customer-service` 已经积累了较完整的微信 UIA/RPA 能力，因此本次重点是迁移自动化能力、接入当前项目协议，并补齐 Windows 微信多账号窗口管理。

短期目标：

1. 消息中心左侧“个人微信”按钮右键打开真实微信登录窗口。
2. 用户在微信窗口中手动完成登录，不由系统代填密码、扫码或绕过风险验证。
3. 采集微信会话及文本、多媒体消息，显示在消息中心。
4. 消息中心输入框发送文本，回写到正确的微信原会话。
5. 在消息链路稳定后接入机器人自动回复。

## 2. 已确认的命名决策

平台内部统一使用：

```text
platform_code = "wechat"
```

“个人微信”仅作为界面显示名称。前端当前使用的 `personal_wechat` 后续应统一为 `wechat`，必要时只保留短期兼容别名，不能让别名继续进入数据库、RPA 事件或任务协议。

需要统一的范围：

- 消息中心平台筛选值。
- `PlatformAccount.platform_code`、`Conversation.platform_code`。
- RPA 事件和任务中的 `platform_code`。
- 机器人平台范围和自动回复配置。
- 平台账号同步、消息查询和发送路由。

## 3. 当前项目与旧项目基线

### 3.1 当前项目已有能力

- Electron 消息中心和平台侧栏。
- 拼多多平台账号、工作区、RPA 节点及任务链路。
- Business API 的 `PlatformAccount`、`Conversation`、`Message`、`RpaEvent`、`RpaTask` 模型。
- 本地 RPA Agent、事件离线队列、事件去重和实时推送。
- 消息中心文本发送和拼多多专用发送桥。

当前差距：

- 侧栏虽显示“个人微信”，右键 IPC 目前只处理拼多多。
- 服务端平台账号 Schema 目前只声明拼多多。
- 消息快照正式协议目前只支持拼多多。
- 微信前端标识和后端/RPA 标识不一致。
- 当前 Electron RPA 账号路由以拼多多工作区为中心，尚无微信窗口/进程管理器。

### 3.2 旧项目可迁移能力

旧项目 `D:\ai-customer-service\python\rpa\platforms\wechat` 已包含：

- 微信窗口探测和健康检查。
- UIA 控件评分与降级选择器。
- 会话列表、未读会话发现和会话切换校验。
- 可见文本及历史消息读取。
- 左右气泡角色判定。
- 文本、图片、表情、文件、视频识别。
- 图片/文件剪贴板提取和截图证据。
- 文本草稿填充、发送按钮多策略点击。
- 观察线程、失败冷却、诊断日志和消息去重。

迁移原则：迁移“平台自动化能力”，不迁移旧项目的 Qt 界面、旧 C++ DAO 或旧业务自动回复闭环。

## 4. 总体架构

```text
消息中心 React UI
        |
        | Electron IPC
        v
微信进程/窗口与账号管理器
        |
        | PID、HWND、本地账号映射
        v
Python RPA Agent
        |
        | 每个微信账号独立 Adapter / Detector / Reader / Sender / Observer
        v
微信原生客户端窗口
        |
        | 本地事件队列、HTTP API、实时事件
        v
Business API
        |
        +-- PlatformAccount / Conversation / Message
        +-- RPA Task / Event
        +-- 机器人自动回复
```

职责边界：

- Electron：启动微信、管理 PID/HWND、绑定本地账号、路由发送任务。
- Python RPA：UIA 探测、消息采集、媒体处理、会话切换和发送。
- Business API：账号、会话、消息持久化，幂等、权限、任务状态和机器人编排。
- React：平台筛选、会话展示、消息展示、输入和状态反馈。

### 阶段 1：右键打开原生微信登录窗口

#### 实施记录（2026-08-08）

- 已新增 Electron 微信可执行文件发现、进程启动、窗口检测和本地账号登记模块。
- 已接入消息中心右键菜单的 `wechat` IPC 分支，菜单项为“打开微信登录窗口”，启动失败通过桌面错误提示反馈。
- 微信路径发现采用分层策略：已保存路径、`WECHAT_EXECUTABLE_PATH`、常见 `Weixin/WeChat` 安装路径；仍找不到时允许用户选择 `.exe`，并持久化到 `wechat-accounts.json`。
- 用户选择路径前会限制为文件名 `Weixin.exe` 或 `WeChat.exe`，避免误启动其他程序。
- 每次右键都会发起一次新的微信启动；启动前保存已有 PID/HWND，启动后只登记新增的非零 HWND，并串行处理连续右键请求。
- 若微信只激活旧实例而没有产生新窗口，返回 `no_new_instance` 并显示明确提示，不重复登记旧账号。
- 当前只记录 PID、HWND、可执行路径、窗口标题和登录状态，不保存密码、二维码或登录凭据。
- 已完成真实 Windows 微信 4.1.12.26 实机验证：连续两次右键可产生两个登录窗口，并可分别登录不同微信账号进入主窗口。
- 已确认两次启动分别登记独立 PID/HWND：测试实例 PID 为 `30912`、`33304`，登记状态均为 `online`。
- 账号记录已写入 Electron `userData` 下的 `wechat-accounts.json`；记录不包含密码、二维码或登录凭据。
- 实机发现微信登录完成后可能重建主窗口，导致同一 PID 的 HWND 变化；当前登记文件不会持续刷新 HWND 和 `last_seen_at`。
- 实机发现历史测试会留下无窗口或已退出的旧 PID 记录，阶段 2 必须完成失效清理、PID/HWND 重绑定和重启恢复。

目标：先完成用户手动登录，不采集消息。

流程：

1. 用户右键消息中心“个人微信”。
2. Electron 主进程调用 Windows 微信启动器。
3. 打开真实微信登录窗口，用户手动扫码或登录。
4. Electron 识别登录窗口和登录完成后的主窗口。
5. 创建本地微信账号记录并保存窗口绑定状态。

账号记录建议包含：

```text
local_account_id
alias
process_id
window_handle
executable_path
login_status
created_at
last_seen_at
```

本阶段验收：右键能打开真实登录窗口；找不到安装路径、取消登录、登录失败和风险验证都有明确提示；不保存密码、二维码或登录凭据。

### 阶段 2：Windows 微信多账号与窗口隔离

#### 进入状态（2026-08-08）

- 多开 Spike 已通过：重复启动产生不同 PID 和主窗口，可登录不同账号，第二次启动不会只激活旧实例。
- 新实例差异检测已按“启动前 PID/HWND 集合 → 启动后新增非零 HWND”实现，连续右键请求已串行化。
- 阶段 2 可以开始实施，但不能直接进入消息采集；应先完成运行中窗口重绑定、旧记录失效处理、账号身份映射和应用重启恢复。

#### 实施记录（2026-08-08）

- 本地账号主键已从 `wechat-pid-*` 迁移为稳定 UUID；PID 只作为本次进程绑定，不再作为账号身份。
- 已实现运行中账号健康刷新：按 PID 更新最新 HWND、登录状态和 `last_seen_at`，支持登录完成后主窗口重建。
- 已实现单账号离线隔离：进程退出后只将对应记录置为 `offline`，清空当前 PID/HWND，并保留 `last_known_process_id` 和历史记录。
- 已实现 Electron 启动恢复：扫描所有非零 HWND 的微信实例；同 PID 恢复原记录，未知 PID 创建独立的待识别账号，不猜测绑定到历史账号。
- 已加入 2 秒健康轮询和退出时清理；新增只读 IPC `wechat:get-accounts` 供后续账号界面和 RPA 路由使用。
- 窗口检测 PowerShell 已强制 UTF-8 输出，并且检测失败会显式报错，不再静默伪装成“没有微信窗口”。
- 已新增多账号隔离测试，覆盖新增实例登记、未产生新实例、HWND 重绑定、单账号离线及未知运行实例恢复。
- 已按产品决定将“微信名 + 微信号”作为当前版本的稳定账号身份（接受两者同时重复的极低概率碰撞）；规范化后计算 SHA-256 派生的 `external_account_id`，同时原样保存 `wechat_name` 和 `wechat_id`。
- 已完成微信 4.1.12.26 实机 UIA 校准：指定 PID/HWND 后从个人卡片的 `display_name_text` 读取微信名，从“微信号：”对应的 `ProfileTextView` 读取微信号；不读取密码、二维码、Token、聊天内容或微信数据文件。
- 已新增 `identity-detector.js` 与 `identity-probe.ps1`。探测只允许操作指定 PID/HWND，短暂打开并关闭个人卡片，恢复鼠标位置和原前台窗口；UIA 浅树、未登录或字段不完整时保持待识别，禁止猜测历史账号。
- 已实现身份匹配后的跨 PID 重绑定：新进程身份与历史 `external_account_id` 完全一致时恢复原 UUID；同一 PID 中检测到账号身份变化时将旧账号置离线，并创建或恢复新账号，避免覆盖历史记录。
- 2026-08-11 根据单账号重启实测调整身份识别触发方式：取消 Electron 启动、2 秒健康轮询以及打开账号列表时的后台自动身份点击。`refreshAccounts()` 现在只读刷新 PID/HWND、在线状态和最后出现时间，绝不操作微信界面。
- 微信平台右键菜单新增“查看已登录账号”。账号弹窗展示已保存的微信名、微信号、窗口在线状态和身份状态；“刷新窗口状态”也是只读操作。
- 身份识别改为明确的人工行为：“识别未确认窗口”串行处理所有在线且尚未确认身份的窗口，已经保存为 `identified` 的在线账号直接跳过；每行“重新识别”允许用户强制复核指定账号。
- 人工识别仍保留跨 PID 重绑定和冲突保护：身份与历史 `external_account_id` 一致时恢复原 UUID；强制复核发现账号已变化时将旧记录置离线并创建或恢复正确账号；同一身份已绑定另一运行窗口时标记冲突。

- 本地记录移除后，现有 `platform_code = "wechat"` 全量同步会将服务端对应账号标记为 `inactive + offline`，不删除会话、消息或其他业务历史。
- 已把微信账号加入当前 RPA 节点账号同步，按 `platform_code = "wechat"` 独立调用 Business API；绑定结果写回本地微信注册表，节点同时声明支持 `pinduoduo` 和 `wechat`。

每个微信账号对应独立运行上下文：

### 阶段 3：微信会话和消息采集

目标：登录后，消息中心显示微信会话、未读数和消息。

主链路：

```text
扫描会话列表
  -> 发现未读会话
  -> 切换并验证目标会话
  -> 读取可见消息
  -> 生成标准 RPA 事件
  -> 写入本地 SQLite 事件队列
  -> 上传 Business API
  -> 实时推送到消息中心
```

旧项目的 observer、UIA reader、角色判断、去重和失败冷却优先迁移。迁移时把窗口定位从“全局微信主窗口”改为“指定账号 HWND/PID”。

消息入库必须携带：

- `platform_code = wechat`。
- `platform_account_id`。
- `conversation_external_id`。
- `platform_message_id` 或稳定降级去重键。
- `sender_role`、`content_type`、`content`。
- `observed_at`、来源、置信度和原始元数据。

历史消息只入库和展示，不触发自动回复；只有确认是实时客户入站消息时才允许进入机器人触发链路。

### 阶段 4：多媒体消息

第一批支持：图片、表情、文件卡片、视频卡片及类型展示。

第二批完善：

- 图片和文件实际资源提取。
- 媒体文件本地落盘或上传服务端。
- `media_resource_id`、受控 URL 和访问权限。
- 消息中心预览、下载和失败状态。

不能把任意本地绝对路径直接暴露给 React。短期可先显示媒体类型和截图证据，随后接入受控媒体资源链路。

### 阶段 5：消息中心发送回微信

目标：输入框发送文本后，写入正确的微信原会话。

推荐链路：

```text
消息中心输入
  -> Business API 创建 send_message RpaTask
  -> Electron 按 platform_account_id 路由到微信账号上下文
  -> 校验窗口和会话标题
  -> 填充微信输入框并发送
  -> 回读发送结果
  -> 完成/失败回传
  -> 消息中心更新状态
```

发送前必须校验：账号在线、窗口存在、会话标题匹配、人工输入框未占用、任务幂等键未执行。第一版接受微信需要前台窗口，不承诺后台静默发送。

### 阶段 6：机器人自动回复

目标：消息链路稳定后，按账号和机器人配置开启自动回复。

```text
客户实时入站消息
  -> Business API 去重
  -> 机器人范围匹配
  -> AI 生成回复
  -> 敏感词/风险策略检查
  -> 创建微信发送任务
  -> 微信窗口发送
  -> 回写结果
```

默认策略：自动回复关闭、人工确认优先。必须支持账号级关闭、会话人工接管、发送失败暂停和风控状态暂停。

## 6. 协议与实现注意事项

### 6.1 事件字段归一化

旧微信事件可使用 `message_observed`、`content_type`、`content` 等字段；当前业务服务已有 `message_snapshot` 和通用 RPA 事件逻辑。应通过适配层统一字段，而不是在每个服务分支中判断旧字段。

### 6.2 账号级串行与跨账号并行

- 同一微信账号内：会话切换、采集和发送必须串行。
- 不同微信账号间：允许并行，但 UIA 调用、剪贴板和前台焦点需要全局互斥保护。
- 一个账号任务失败后，只暂停该账号队列。

### 6.3 本地离线队列

微信 RPA 采集事件先写本地 SQLite，再上传服务端。网络恢复后按 `event_id`、`dedup_key` 和 `platform_message_id` 补传，服务端幂等入库。

### 6.4 媒体资源

媒体文件建议经过受控上传或 Electron IPC 代理读取，消息原文只保存资源引用、类型、哈希和提取状态。

## 8. 主要风险

1. 微信版本的多开行为可能变化，必须先做 Spike，不能假设重复启动一定多开。
2. 微信 4.x Qt Quick/QML 控件暴露程度可能变化，UIA 选择器需要诊断和降级。
3. 多窗口同时操作存在焦点争抢，必须使用账号级队列和 UIA 互斥。
4. 微信发送通常依赖前台窗口，后台静默发送不能作为第一版承诺。
5. 图片、文件和视频需要受控媒体资源链路，不能直接暴露本地路径。
6. 账号、会话和消息必须始终携带 `platform_account_id`，避免多账号串数据。
7. 风控、登录失效和无法确认发送结果时，应停止操作并转人工，禁止盲目重试。

## 9. 建议执行顺序

1. 统一所有代码和协议中的平台标识为 `wechat`。
2. 完成 Windows 微信多开可行性 Spike。
3. 实现 Electron 微信进程管理、右键启动和本地账号绑定。
4. 迁移旧项目微信 RPA 内核，先接健康检查和手动连接。
5. 接入文本会话采集和消息中心展示。
6. 接入多媒体消息和媒体资源。
7. 接入消息中心文本发送。
8. 最后开启账号级机器人自动回复。
