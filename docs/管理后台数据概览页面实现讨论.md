这个收缩范围很合适。当前“数据概览”全部是 mock，包括固定日期、八个指标、流量曲线和热门分类，来源分别在 [constants.ts (line 92)](D:/project-electron/ai-customer-service/apps/desktop/src/admin/constants.ts:92) 和 [AdminWorkspace.tsx (line 677)](D:/project-electron/ai-customer-service/apps/desktop/src/admin/views/AdminWorkspace.tsx:677)。

建议第一版只展示 3 个真实指标，其他 5 个先隐藏，不要展示为 `0`，避免用户误以为已经统计。

**指标口径**

- `今日消息数`
  - 统计今天实际发送成功或采集到的客户消息与客服消息总数。
  - 排除 `demo`、发送失败和仍在排队的消息。
  - 优先按平台消息时间 `platform_sent_at` 判断是否属于今天；没有平台时间时再使用本地消息时间。
  - 这样启动 RPA 后导入的历史消息不会错误计入今天。
- `独立接待率`
  - 建议定义为：`全程由机器人回复的已接待会话数 / 今日已有回复的会话数`。
  - “全程由机器人回复”要求该会话今日回复均能关联到成功的 `AutomationReplyRun`，且没有人工发送记录。
  - 等待回复中的会话不进入分母，避免新消息刚到就把比率拉低。
  - 当前 `AutomationReplyRun` 已经记录机器人、来源客户消息和回复消息，具备基础统计条件：[entities.py (line 445)](D:/project-electron/ai-customer-service/services/business-api/app/models/entities.py:445)
- `平均响应时间`
  - 从客户消息被 RPA 实际采集的 `observed_at` 开始，到发送任务真实完成的 `RpaTask.completed_at` 为止。
  - 不能使用回复消息创建时间，因为机器人创建发送任务时消息只是 `queued`，并不代表原平台已经发送成功。
  - 只统计完成发送的机器人回复，失败和未发送的不计入。

“独立接待率”初期可能会偏低，因为当前人工发送和机器人发送最后都可能表现为 `source="desktop"`。不过机器人回复可以通过 `AutomationReplyRun.reply_message_id` 精确识别，剩余客服消息即可判为人工回复，因此不需要立即修改消息表结构。

**流量监控**

建议统计“今日客户入站消息量”，不统计机器人和人工回复，否则它只是消息总量的另一种图形表达。

- 横轴按小时展示 `00:00–23:00`。
- 数据少时也保持 24 个时间点，空时段补 `0`。
- 时间依据与“今日消息数”一致，避免历史采集污染。
- 前端继续复用现有面积图，只将 `CHART_DATA` 换成接口数据即可。

如果后面希望展示“咨询会话数”，可以再提供一个切换项：

- 客户消息量
- 独立客户/会话数

第一版只做客户消息量即可。

**热门咨询分类**

这里需要区分两个概念：

1. QA 分类是知识库内容分类；
2. 客户咨询只有真正命中某条 QA 时，才能确定属于该分类。

当前 AI 回复结果里已经包含完整 `qa_match.entry`，问答记录也有 `category_id/category`，但 `AutomationReplyRun` 目前只持久化了 `decision`、`trace_id` 和回复消息，没有保存命中的 QA 分类。因此目前无法准确统计“今日各分类命中次数”。

建议在回复运行记录中补充：

- `intent`
- `qa_entry_id`
- `qa_category_id`
- `qa_category_name`
- `qa_match_type`

然后“热门咨询分类”第一版明确统计：

> 今日命中 QA 问答知识库的咨询分类分布

按分类聚合当天命中次数，显示前 5 名和占 QA 命中总数的百分比。未命中 QA、继续走产品文档检索的咨询暂不归类，避免强行归到不准确的 QA 分类。

不能直接使用 QA 问答的 `call_count` 来做今日热门分类，因为它是累计调用次数，没有日期维度，而且可能无法严格按当前登录用户统计。

我建议最终口径如下。

**八个指标**

真实指标：

- 今日消息数
- 独立接待率
- 平均响应时间

开发中指标：

- 有效恢复率
- 订单转化率
- 满意度
- 转人工率
- 撤回率

开发中卡片不要继续显示 mock 数字，建议展示：

- 数值：`--`
- 右上角：`开发中`
- 底部：`暂未接入统计`
- 使用灰色样式，不显示虚假的环比百分比

真实指标也暂时不展示 mock 环比，底部改成“更新于 15:30:20”。后面接入昨日同期计算后，再恢复涨跌百分比。

**日期选择**

现有固定日期应改成真正的日期区间选择，默认选择今天。

建议提供：

- 开始日期
- 结束日期
- 查询按钮
- 快捷选项：今日、昨日、近 7 天、近 30 天
- 结束日期不能早于开始日期
- 暂时限制最长查询 90 天，避免本地数据库聚合过重

时间统一使用桌面端所在时区，即 `Asia/Shanghai`，后端按照：

```
开始日期 00:00:00（包含）
到结束日期下一天 00:00:00（不包含）
```

来查询，避免结束日期当天晚上数据遗漏。

日期范围变化后，这三个指标、流量监控和热门咨询分类一起刷新。

这里有一个文案细节：当选择的不只是今天时，“今日消息数”会变得不准确。建议动态显示：

- 选择今天：`今日消息数`
- 选择其他单日：`当日消息数`
- 选择日期范围：`消息总数`

右上角标签也从“今日”动态变成“所选时段”。

**流量监控**

建议根据日期范围切换粒度：

- 单日：按小时统计，横轴 `00:00–23:00`
- 2–31 天：按天统计，横轴显示 `08-01、08-02`
- 32–90 天：仍按天统计，但减少横轴标签密度

统计对象仍建议使用客户入站消息量，这样图表表达的是实际咨询流量，而不是包含客服回复后的消息总量。

**热门咨询分类**

可以加入“文档检索”，处理顺序建议为：

1. 命中 QA：使用对应 QA 分类，如“物流问题”
2. 未命中 QA，但召回了产品文档片段：归入“文档检索”
3. QA 未命中且没有文档召回：暂不纳入热门分类

例如：

```
常见问题       38%
商品问题       26%
物流问题       18%
文档检索       12%
售后退款        6%
```

不过“文档检索”严格说属于知识来源，不是业务意图分类。作为当前 MVP 放在热门咨询分类里没有问题，但后端应保留类型：

```
{
  "type": "document_retrieval",
  "name": "文档检索",
  "count": 12
}
```

QA 分类则返回：

```
{
  "type": "qa_category",
  "category_id": "...",
  "name": "物流问题",
  "count": 18
}
```

这样以后如果将页面拆成“热门咨询意图”和“知识来源分布”，不用重新迁移统计数据。

要实现准确统计，需要在每次自动回复运行中持久化以下摘要：

- QA 是否命中
- QA 问答 ID
- QA 分类 ID 和分类名称
- 是否执行文档检索
- 文档召回片段数量
- 意图名称
- 回复决策
- 完成时间

当前这些数据已经存在于 AI 回复结果中，只是还没有完整写入 `AutomationReplyRun`。

**查看完整报告**
