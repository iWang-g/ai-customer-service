# 拼多多接口主链路实施方案

## 1. 背景和目标

当前拼多多工作区已经支持多店铺页面会话、会话采集、消息采集、客户订单采集和消息发送，但主链路依赖 DOM 操作。实测问题集中在：

- 切换会话慢，影响客服正在使用的页面。
- DOM 结构和渲染时机不稳定，导致采集失败或误判。
- 历史消息、实时消息、订单卡片需要页面加载到对应区域后才能读取，效率低。
- 自动发送依赖输入框注入和按钮点击，确认链路长。

本方案将拼多多能力改造为接口主链路：

1. 通过接口获取各个店铺页面指定客户的历史聊天消息。
2. 某个店铺页面有客户新消息时，系统能马上知道。
3. 通过接口给客户发送消息。
4. 通过接口获取客户订单信息。

DOM 只保留为登录状态、风控状态等页面健康判断的兜底手段；店铺名、会话、消息、订单、发送均优先来自接口。

## 2. 运行边界

拼多多各店铺仍由用户人工登录。桌面端继续保持当前多账号隔离模型：

```text
一个本地店铺账号
  -> 一个 Electron partition
  -> 一个拼多多 WebContentsView
  -> 一个页面内接口客户端
```

页面内接口客户端运行在对应店铺的拼多多页面中，复用当前页面的 Cookie、登录态、localStorage、风控上下文和同源权限。主进程和业务服务端不直接保存或拼接 Cookie。

接口主链路不假设平台接口永久不变；短期目标是先解决当前 DOM 慢和不稳定的问题。如果后续拼多多接口字段或路径变化，再按新页面抓包结果更新适配器。

## 3. 总体架构

新增“PDD 页面内 API Client”，承接原 preload 中的数据采集和发送职责：

```text
拼多多人工登录页面
  -> 页面内 API Client
     -> 请求/响应捕获
     -> 主动同源 fetch
     -> anti_content 和 sync_key 运行态缓存
     -> 接口响应归一化
  -> Electron 主进程 PddCollectionRuntime
  -> RPA 事件队列
  -> business-api 入库和 WebSocket 通知
```

保留现有 `PddCollectionRuntime`、RPA 离线队列、服务端幂等入库逻辑。接口适配器输出继续使用当前项目已有的事件形态：

- `conversation_snapshot`
- `message_snapshot`
- `customer_orders_snapshot`
- 后续发送成功补充 `agent_message` 或并入消息快照确认

## 4. 接口来源和运行态参数

### 4.1 请求捕获

页面内 API Client 需要 wrap 页面上下文的 `fetch` 和 `XMLHttpRequest`，捕获以下接口的请求参数和响应：

- `POST /plateau/chat/latest_conversations`
- `POST /plateau/chat/list`
- `POST /plateau/sync/message`
- 文本发送接口，例如 `send_message`
- 订单相关接口，按后续抓包结果补齐

捕获目的：

- 获取页面自己生成的 `anti-content` header。
- 获取 body 中的 `anti_content`。
- 获取 `sync/message` 当前 `seq_id`。
- 获取接口原始响应，用于实时更新本地状态。
- 记录接口字段变化诊断，不记录 Cookie、账号密码和敏感 token。

### 4.2 主动同源 fetch

当系统需要拉历史消息、查订单或发送消息时，由页面内 API Client 发起同源请求：

```js
fetch(url, {
  method: 'POST',
  credentials: 'include',
  headers: {
    accept: '*/*',
    'content-type': 'application/json',
    'anti-content': latestAntiContentHeader,
  },
  body: JSON.stringify(payload),
});
```

`anti_content` 不能复制抓包文档中的固定值。适配器按以下策略处理：

1. 优先使用页面最近一次同类请求捕获到的 `anti-content` header 和 body `anti_content`。
2. 如果主动请求返回风控、失败或参数错误，触发页面原生会话刷新或等待下一次平台原生请求，刷新运行态参数。
3. 连续失败时上报 `api_runtime_parameter_invalid` 诊断，并降级为“需要人工检查页面状态”。

## 5. 店铺身份识别

店铺名不再依赖 DOM 识别，也不再从会话列表接口 `latest_conversations` 推导。店铺身份改为使用专用店铺信息接口：

```text
POST /janus/api/customService/queryCustomServiceInfo
```

核心响应字段：

```json
{
  "success": true,
  "result": {
    "mallInfoResult": {
      "mallId": 941637564,
      "logo": "http://...",
      "mallName": "小王家的网店8756"
    }
  }
}
```

兜底接口：

```text
GET /chats/userinfo/realtime?get_response=true
```

核心响应字段：

```json
{
  "mall_id": 941637564,
  "mall": {
    "mall_id": 941637564,
    "mall_name": "小王家的网店8756",
    "logo": "http://..."
  }
}
```

识别策略：

1. 页面在线且已有运行态 `anti-content` 后，主动调用 `queryCustomServiceInfo`。
2. 如果主接口失败或缺少 `mallInfoResult.mallId/mallName`，再调用 `userinfo/realtime` 兜底。
3. `external_account_id` 使用 `mallId`/`mall_id`，店铺别名使用 `mallName`/`mall_name`。
4. 如果专用店铺信息接口仍无有效店铺身份，保留原账号别名，不回退到 DOM 店铺名识别。
5. `latest_conversations` 继续用于会话列表、未读轮询和最新消息补采，但不再作为店铺身份来源。

## 6. 会话和历史消息

### 6.1 会话列表

使用：

```text
POST /plateau/chat/latest_conversations
```

核心字段映射：

| 拼多多字段 | 本项目字段 | 说明 |
| --- | --- | --- |
| `user_info.uid`  | `external_conversation_id` | 客户稳定唯一标识 |
| `user_info.nickname` | `customer_name` | 展示名，不用于唯一识别 |
| `user_info.avatar` | `avatar_url` | 客户头像 |
| `content` | `latest_message_text` | 最新消息摘要 |
| `last_unreply_time`、状态字段 | `unread_count`/未回复状态 | 视接口字段再细化 |
| `mallName` | `platformAccountName`/店铺别名 | 店铺名来源 |

会话 key 统一为客户 `uid`：

```text
conversation_external_id = String(customer_uid)
```

如果响应中缺少客户 uid，则该会话不进入自动发送和订单查询主链路，只作为异常诊断记录。

### 6.2 指定客户历史消息

使用：

```text
POST /plateau/chat/list
```

请求关键参数：

```json
{
  "data": {
    "cmd": "list",
    "request_id": 1787022500409,
    "list": {
      "with": {
        "role": "user",
        "id": "9195398176930"
      },
      "start_msg_id": null,
      "start_index": 0,
      "size": 50
    },
    "notUpdateUnreplyTs": true,
    "anti_content": "<runtime value>"
  },
  "client": "WEB",
  "anti_content": "<runtime value>"
}
```

分页策略：

- 默认拉取最近 50 至 100 条。
- 如果 `has_more=true` 且业务需要全量补齐，再使用 `start_msg_id` 或接口实际分页字段继续向前拉。
- 每个客户历史补采设置最大消息数，避免单次任务过重。

消息字段映射：

| 拼多多字段 | 本项目字段 | 说明 |
| --- | --- | --- |
| `msg_id` | `platform_message_id` | 消息幂等主键 |
| `pre_msg_id` | `structured_payload.pre_msg_id` | 消息链路和排序参考 |
| `from.role=user` | `sender_role=customer` | 客户消息 |
| `from.role=mall_cs` | `sender_role=agent` | 客服消息 |
| `type=0` | `message_type=text` | 文本 |
| `type=1` | `message_type=image` | 图片 |
| `content` | `content`/`image_url` | 按类型拆分 |
| `ts` | `platform_sent_at` | 平台发送时间 |

排序规则：

1. 优先按 `ts` 升序。
2. 同秒消息按 `msg_id` 升序。
3. 如需严格还原链路，使用 `pre_msg_id` 构建链表并校验缺口。

## 7. 实时消息

主链路使用：

```text
POST /plateau/chat/latest_conversations
POST /plateau/chat/list
```

辅助观察：

```text
POST /plateau/sync/message
```

实测结论：`sync/message` 有时能返回消息正文，但大部分情况下只表示同步活动，甚至无法稳定说明具体哪个会话有新消息。因此它不能作为实时消息正文主来源。

启动策略：

1. 页面在线后启动 `latest_conversations` 定时轮询，默认 2 秒一次。
2. 每次读取接口返回的会话列表，筛选 `status=unread` 的会话。
3. 对每个未读会话的 `user_info.uid` 调用 `chat/list` 补采最近历史消息。
4. 如果该 UID 在本地数据库还没有会话，`chat/list` 映射入库时直接创建会话。
5. `sync/message` 保留捕获和低频轮询，作为诊断、gap 辅助和偶发消息正文来源，不再作为是否刷新未读的前置条件。

轮询策略：

- 在线页面默认每 2 秒轮询一次 `latest_conversations`。
- 可能存在多个未读会话，按接口返回顺序逐个 `chat/list`。
- 实时补采不清空已有去重/RPA 记录，依赖 `msg_id` 幂等入库。
- `sync/message` 出现 `has_gap=true` 且能定位客户 uid 时，可额外触发一次 `chat/list` 补齐历史。
- 出现风控或登录失效时停止主动轮询，状态切为 `risk_control` 或 `login_required`。

实时消息处理：

- `chat/list` 中 `from.role=user` 的新增消息生成客户入站事件。
- `from.role=mall_cs` 的消息用于确认客服发送结果和本地去重。
- 图片消息直接保存图片 URL，不通过 DOM 读取图片。

## 8. 接口发送消息

使用抓包确认的发送消息接口，目标是替换输入框注入和按钮点击。

### 8.1 文本消息

发送前置条件：

- 已知客户 `uid`。
- 当前店铺页面在线。
- 已有可用 `anti_content` 运行态参数。
- 同一店铺发送任务进入串行队列。

发送流程：

```text
消息中心手动发送或业务服务端产生发送任务
  -> Electron 主进程定位对应店铺 partition
  -> 页面内 API Client 调用 send_message
  -> 返回 msg_id/pre_msg_id/ts
  -> 以 msg_id 作为 platform_message_id 生成本地 agent 消息
  -> 立即对该客户 uid 做一次 chat/list 补采
  -> chat/list 回来后按同一 msg_id 更新/补齐消息字段
```

`send_message` 成功响应示例：

```json
{
  "success": true,
  "result": {
    "response": "send_message",
    "request_id": 1787031726880,
    "result": "ok",
    "msg_id": 1787031727088,
    "pre_msg_id": "1786933622874",
    "ts": 1787031727
  }
}
```

消息中心输入框手动发送文本消息也走上述接口链路，不再使用原平台输入框注入和 Enter 发送。接口成功后即可直接把 `msg_id` 写入业务库；后续 `chat/list` 获取到相同 `msg_id` 时只更新/补齐，不重复插入。

失败处理：

- 参数失效：刷新 `anti_content` 后重试一次。
- 登录失效：任务失败并提示人工登录。
- 风控：任务挂起，不继续自动重试。
- 接口返回非成功：记录原始错误码和简短错误信息。
- 已知客户 uid 的文本发送失败时，不回退到 DOM 输入框注入，避免形成两套不可区分的发送链路。

发送幂等：

- 业务任务有自己的 `task_id`。
- 平台成功后以 `msg_id` 为准。
- 未拿到 `msg_id` 但接口超时时，不盲目重发，先通过 `chat/list` 查询该会话最新消息确认是否已经发送成功。
- `sync/message` 只作为诊断或辅助信号，不再作为发送确认主依据。

### 8.2 图片消息

图片发送也走接口主链路，不再使用原平台输入框粘贴图片和 Enter 发送。

图片发送分三步：

```text
消息中心手动发送图片或业务服务端产生图片任务
  -> Electron 主进程读取远程图片或 dataURL，得到 imageDataUrl/尺寸/字节数
  -> 页面内 API Client 调用 /plateau/file/pre_upload
  -> 使用 pre_upload 返回的 upload_signature/upload_url 调用 https://file.pinduoduo.com/v2/store_image
  -> 使用 store_image 返回的 chat-img URL 调用 /plateau/chat/send_message
  -> 返回 msg_id/pre_msg_id/ts
  -> 对该客户 uid 做一次 chat/list 补采
```

`pre_upload` 请求核心结构：

```json
{
  "chat_type_id": 1,
  "file_usage": 1
}
```

`store_image` 请求核心结构：

```json
{
  "image": "data:image/jpeg;base64,...",
  "upload_sign": "<upload_signature>"
}
```

`send_message` 图片消息核心字段：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `message.type` | `1` | 图片消息 |
| `message.content` | `https://chat-img.pddugc.com/...` | `store_image` 返回的图片 URL |
| `message.hash` | 图片内容 hash | 优先使用上传响应 hash；没有则使用本地图片字节 hash |
| `message.size.width` | 图片宽度 | 优先使用上传响应宽度 |
| `message.size.height` | 图片高度 | 优先使用上传响应高度 |
| `message.size.image_size` | 图片 KB 大小 | 至少为 1 |
| `message.info.thumb_data` | 图片 dataURL | 与抓包中的缩略图字段保持一致 |

成功判定仍以 `send_message` 响应中的 `msg_id` 为准。后续 `chat/list` 获取到同一 `msg_id` 时只更新/补齐，不重复插入。

验证日志：

- `api_image_send_requested`
- `api_image_upload_succeeded`
- `api_image_send_succeeded`
- `api_image_send_chat_list_backfill_completed`

如果图片接口发送失败，记录 `api_image_send_failed_no_dom_fallback`，不自动回退到 DOM 粘贴发送，避免两套发送链路混用。

## 9. 客户订单接口

订单接口需要根据后续抓包补齐路径和请求体。实施方式保持和聊天接口一致：

1. 页面内捕获用户打开订单区域时的订单接口请求。
2. 识别请求中客户 uid、订单分页、订单状态等参数。
3. 主动同源 fetch 获取指定客户订单。
4. 归一化为当前项目已有 `customer_orders_snapshot`。

目标字段：

| 本项目字段 | 来源 |
| --- | --- |
| `platform_order_id` | 拼多多订单号 |
| `goods_id` | 订单主商品 `goodsId`，用于同客户同商品话术去重 |
| `raw_status` | 平台原始主状态文案，来自 `orderStatusStr` |
| `status` | 本项目归一化状态 |
| `ordered_at` | 下单/支付时间 |
| `products` | 商品标题、规格、数量、图片、商品 ID，商品项保留 `goods_id` |
| `order_amount` | 订单原价 |
| `discount_amount` | 优惠金额 |
| `paid_amount` | 实付金额 |
| `after_sale` | 售后状态、退款状态等，仅记录和展示，不默认阻断签收后关怀 |

如果订单接口暂时只拿到部分字段，也先落库 `raw_payload` 或 `raw_text` 诊断字段，保证后续可迭代归一化。

签收后关怀使用订单接口主状态判断：`orderStatusStr` 为“已签收”才创建或放行发送候选；`afterSalesInfo`、`workbenchOrderTagNew`、`compensate` 等辅助字段保留展示和诊断价值，但不作为默认硬阻断。

## 10. 改造模块

### 10.1 桌面端

重点文件：

```text
apps/desktop/electron/platform-workspace/pinduoduo/preload.cjs
apps/desktop/electron/platform-workspace/pinduoduo/reader.js
apps/desktop/electron/platform-workspace/pinduoduo/runtime.js
apps/desktop/electron/platform-workspace/workspace-manager.js
```

建议新增：

```text
apps/desktop/electron/platform-workspace/pinduoduo/api-client.cjs
apps/desktop/electron/platform-workspace/pinduoduo/api-mapper.cjs
```

职责划分：

- `api-client.cjs`：请求捕获、主动 fetch、运行态参数缓存、轮询。
- `api-mapper.cjs`：接口响应到项目 payload 的纯函数转换，方便自动化测试。
- `preload.cjs`：保留页面状态判断、IPC 命令入口和少量 DOM 兜底。
- `reader.js`：继续做字段清洗、长度限制和 schema 防护。
- `runtime.js`：继续做事件展开、幂等和 RPA 入队。
- `workspace-manager.js`：把原本 `collect-conversation`、`send-message`、`refresh-customer-orders` 命令切到接口命令。

### 10.2 服务端

服务端优先复用现有事件和消息模型。需要检查和补充：

- `platform_message_id` 长度是否满足拼多多 `msg_id`。
- `conversation_external_id` 改为客户 uid 后，旧 DOM name hash 会话是否需要迁移或并存。
- 订单快照字段是否足够承载接口返回的商品、售后和金额。
- 发送任务状态是否能表达“接口返回未知，等待 chat/list 确认”。

## 11. 兼容和迁移

历史 DOM 会话可能使用以下外部 ID：

```text
data-random 首段数字
name:<hash>
```

接口改造后统一使用客户 `uid`。迁移策略：

1. 新采集数据优先使用 uid。
2. 如果旧会话只有昵称，暂不自动合并，避免误合并同名客户。
3. 如果旧会话中已有可以映射到 uid 的消息或后续人工确认，再做一次性合并。
4. 消息层以 `platform_message_id=msg_id` 去重，新旧 DOM 消息 ID 不一致时允许短期并存，后续通过内容和时间人工清理。

## 12. 验证计划

### 12.1 离线单元测试

用 `接口分析.md` 中的脱敏响应样本构造 fixture，验证：

- `latest_conversations` 能映射出店铺名、客户 uid、昵称、头像、最新消息。
- `chat/list` 能映射文本和图片消息。
- `sync/message` 能映射实时客户入站消息。
- `send_message` 响应能映射发送成功确认。
- 异常字段、空数组、缺 uid、缺 msg_id 时不会抛出未捕获异常。

### 12.2 页面内集成测试

人工登录测试店铺后验证：

1. 打开拼多多工作区，不点击会话，也能通过 `latest_conversations` 识别店铺名。
2. 输入客户 uid，能拉取该客户历史消息。
3. 买家发新消息，系统在 1 至 3 秒内收到入站事件。


- `summarizeMappedSnapshot()` 输出 `sync_gap_count` 和 `sync_gap_customer_uids`。

主进程：

- 如果 `sync/message` 返回 `has_gap=true` 或 `reset_seq_id=true`，且响应中能定位客户 uid，则排队执行一次 `chat/list` 补采。
- 补采使用现有 `collect-conversation-api`/`chat/list` 接口链路，不切 DOM 会话。
- 同一店铺同一客户设置 30 秒冷却，避免 gap 状态持续时反复补采。
- 如果 gap 响应没有客户 uid，只记录 `api_sync_gap_backfill_skipped`，不盲目扫描 DOM。

## 20. DOM 未读触发改为 API 补采

完成日期：2026-08-19

本阶段处理“双链路并存”问题：页面 DOM 扫描仍可发现未读会话，但不再把“切会话后读取聊天 DOM 消息区”作为主动作。

### 20.1 新流程

1. DOM 扫描只负责发现未读会话，并上报 `collect_unread_request`，其中 `conversation_key` 优先为客户 UID。
2. 主进程收到未读请求后，如果 `conversation_key` 是客户 UID，先调用页面内 `collect-conversation-api`，实际请求 `POST /plateau/chat/list`。
3. `chat/list` 映射成功并写入 runtime 后，主进程记录 `dom_unread_api_backfill_succeeded`，并向页面发送 `ack-unread-api-backfill`。
4. 页面收到 ack 后，仅把当前未读预览版本标记为已处理；如没有人工操作暂停，会点击该会话用于同步页面已读状态，但不读取聊天消息区、不发 DOM snapshot。
5. 如果缺少 UID（例如旧 `name:` key），先执行 DOM 切会话定位，但该步骤只验证会话切换，不读取消息区、不发 DOM snapshot。
6. DOM 定位后主动刷新 `latest_conversations`，按客户昵称和预览文本解析客户 UID，再继续走 `chat/list`。
7. 如果仍无法解析 UID 或 `chat/list` 失败，本次未读补采失败并记录日志，不再降级到 DOM 读消息流程。

### 20.2 关键日志

- `dom_unread_api_backfill_requested`：DOM 未读已转为 API 补采请求。
- `api_chat_list_import_requested` / `api_chat_list_import_succeeded`：实际 `chat/list` 请求和入库结果。
- `dom_unread_api_backfill_succeeded`：未读会话已由 API 主链路补采成功。
- `dom_unread_api_backfill_acknowledged`：页面侧已复位未读请求状态，避免同一预览反复触发。
- `dom_unread_api_backfill_requires_dom_switch`：缺少 UID，需要先 DOM 切换定位。
- `dom_unread_api_backfill_uid_resolved`：DOM 定位后已通过 `latest_conversations` 解析出 UID。
- `dom_unread_api_backfill_failed_no_dom_message_fallback`：API 补采失败，且不会再回落 DOM 读消息区。

预期实机观察：有 UID 的新未读消息到达后，应看到 `dom_unread_api_backfill_*` 和 `api_chat_list_import_*`，不应再看到对应的 `unread_processing_started`。无 UID 时可以看到 `dom_conversation_switch_requested_for_api_backfill`，但不应出现 DOM 读消息区产生的 snapshot。

## 21. 实时消息改为 latest_conversations 轮询

完成日期：2026-08-19

本阶段基于实机连续发消息测试调整实时入口：`sync/message` 保留捕获和辅助轮询，但不再决定是否刷新未读会话。页面在线后直接每 2 秒调用一次 `POST /plateau/chat/latest_conversations`。

### 21.1 新主链路

```text
页面在线
  -> 2 秒轮询 latest_conversations
  -> 筛选 status=unread 的会话
  -> 逐个按 user_info.uid 调用 chat/list
  -> chat/list 快照入库，缺失会话自动创建
  -> runtime/RPA 按 msg_id 幂等处理新增客户消息
```

### 21.2 实施细节

- 页面侧新增 `latest_conversations` 轮询器，和 `sync/message` 辅助轮询一起随在线状态启动/停止。
- 主进程允许无 pending 的 `api_latest_conversations_result` 作为实时轮询事件处理。
- 实时轮询来源的 unread 会话不再使用 30 秒摘要版本跳过，避免连续消息摘要未变化时漏补采。
- 实时补采仍使用 `clearBeforeImport=false`，不清空已有消息去重和 RPA 记录。
- DOM 未读检测继续只作为诊断观察，不再触发消息区读取。

### 21.3 关键日志

- `api_latest_conversations_polling_started` / `api_latest_conversations_polling_stopped`
- `api_latest_unread_poll_received`
- `api_latest_unread_backfill_queued`
- `api_latest_unread_candidates_resolved`
- `api_chat_list_import_requested`
- `api_chat_list_import_succeeded`
- `api_latest_unread_backfill_completed`

预期实机观察：客户连续发送多条消息时，即使 `sync/message` 没有消息正文或没有推进，也应每 2 秒看到 `latest_conversations` 轮询；只要接口返回 `status=unread`，对应 UID 就会触发 `chat/list` 补采。本地不存在该 UID 会话时，由 `chat/list` 入库创建。

## 22. chat/list 消息顺序改为 msg_id 主导

完成日期：2026-08-19

实测确认：`POST /plateau/chat/list` 返回的聊天消息具备稳定 `msg_id`，且后一条消息的 `msg_id` 大于前一条消息。因此 API 主链路不再依赖 DOM 快照重叠和“会话消息队列”来判断聊天顺序。

### 22.1 新规则

- `chat/list` 快照来源为 `pdd-api-list-*` 时，后端按 `platform_message_id/msg_id` 数值升序处理消息。
- 已存在相同 `platform_message_id` 的消息只更新内容和平台回显信息，不重复写入。
- 新 `platform_message_id` 按平台 ID 顺序写入；前端展示拼多多消息时也按平台 ID 排序。
- 如果某个 API 快照没有任何已知平台 ID 锚点，按 bootstrap 导入，避免把整段历史误判为实时新消息触发自动回复。
- 旧 DOM 快照对齐逻辑保留为诊断能力，但不再面向用户弹出“消息序列无法安全衔接/重建消息队列”提示。

### 22.2 用户界面

- 聊天窗口不再显示“该会话的消息序列无法安全衔接”提示条。
- 会话列表不再显示“消息序列同步异常”三角标。
- “重建消息队列”不再作为当前拼多多 API 主链路的用户操作入口。

## 23. latest_conversations 轮询增加最新 msg_id 查库过滤

完成日期：2026-08-19

`latest_conversations` 响应中包含每个会话最新一条消息的 `msg_id`。实时轮询不应只看 `status=unread`，因为客服发送的新消息通常不会让会话处于 unread，但仍需要被采集入库。

### 23.1 新触发条件

每 2 秒轮询 `latest_conversations` 后，对每个有客户 UID 的会话执行以下判断：

1. 如果响应有 `latest_msg_id`，先查询本地业务库中该店铺、该客户 UID、该 `platform_message_id` 是否已存在。
2. 如果已存在，跳过该会话，不调用 `chat/list`。
3. 如果不存在，说明该会话至少有一条消息尚未采集，调用 `chat/list` 补采。
4. 如果查询失败，保守调用 `chat/list`，避免漏消息。
5. 如果响应没有 `latest_msg_id`，但会话 `status=unread`，仍调用 `chat/list`。

### 23.2 影响

- 客户新消息：通常 `status=unread` 且最新 `msg_id` 不存在，会触发 `chat/list`。
- 客服新消息：即使 `status=read`，只要最新 `msg_id` 不存在，也会触发 `chat/list`。
- 已采集会话：最新 `msg_id` 已存在时跳过，降低无效 `chat/list` 请求。
- 本地不存在的会话：查库结果为不存在，触发 `chat/list` 后由入库链路创建会话。

## 25. 2026-09-19：图片与未知卡片先理解，转接作为最后处理手段

本轮已实现，待真实店铺验收。复用拼多多现有消息采集、文本发送、客户订单和商品卡上下文；无需数据库迁移。

### 25.1 消息入口与上下文

- 文本、商品卡、订单卡继续使用原解析；未知消息即使没有字符串正文，也保留占位消息，不再直接丢弃。
- 未知卡片从 `content/info/biz_context` 投影核心 JSON：正文、标题、状态描述、商品/订单 ID 等。最多 32 个字段、5 层、300 个节点、约 4KB，保留截断和解析失败标记。读取时不执行 getter、脚本或按钮。
- 核心字段过滤按钮、跳转、凭证及明显收货信息；这是有限字段清理，不代表对任意自然语言进行了完整隐私识别。原始采集审计与供 AI 使用的核心投影分开处理。
- 服务端先校验原始快照哈希，再整理正式消息，保留原有采集协议、平台消息 ID 去重、增量和启动未读判定。系统、转接、来源提示不因新增类型而触发回复。
- 买家图片以 `pdd_unread_image` 和无识图标记进入上下文，不传图片 URL 给模型；未知卡片以 `pdd_unknown_message`、未核验标记进入上下文。两者不再因类型未知而在模型之前强制走人工分支。
- 实际发送成功的原平台客服文字进入聊天历史；排队、失败、取消、结果待确认的回复不算已经问过客户。

### 25.2 决策边界

拼多多增加独立策略提示。先判断诉求，再决定是否使用 QA、商品/订单资料或文档：有可靠依据就答，意思不明且追问有价值就简短问，明确需要人工办理或仍无法处理才转人工。

纯图片并不等于客户要求卖家发图。没有识图能力时不能描述图片、识别图中文字。对同一未解决问题原则上主要澄清一次；以实际聊天历史和模型判断为准，不新增硬性计数器。补充后能回答就回答，新话题重新判断，致谢不触发转接。

退款、地址、定制等词语本身不决定转接；咨询规则可根据适用资料回答，明确办理请求优先于 QA。卡片按钮不视为买家已经提交办理意愿，未知数值状态不翻译成平台事实。

普通文字咨询在意图检查后仍可复用 QA 答案及配图；图片/未知卡片的 QA 命中只作为生成依据，不直接将占位或卡片关键词命中的固定答案发送出去。知识生成使用结构化 `answerable/needs_clarification/text/reason`，不足以回答时进入人工决策。未绑定知识库不直接等于不能回答。

现有纯商品卡固定引导、已配置邮件交付和定制补充话术保留；人工办理和合理追问优先于定制补充话术。此次未新增拼多多商品规格详情采集或视觉识别。

### 25.3 自动转接

选择机器人“转移会话给客服”后，新流程为：

`preparing（查询目标）→ ack_queued（为您转接中）→ ready → transferring → transferred / confirmation_pending`

- 复用 `getAssignCsList` 与 `move_conversation`。列表必须 HTTP 成功、业务成功且结构正确；缺字段/错误返回不能伪装成空列表。
- 当前客服身份必须可识别，排除本人；首版只使用 `recvUser=1` 的其他客服，随机选一个。此字段暂按保守的可接待条件使用，未将其定义为完整在线状态枚举，真实平台含义仍需结合使用结果确认。
- 真正没有合格目标时记录 `unavailable`，准备阶段不发转接告知，不标记持续待人工。新问题可正常回复，新消息需要人工时可再次查询，同一来源消息不重复尝试。
- 发送告知后，提交前重新查询和验证目标；目标消失但还有其他目标时本次失败，不擅自改转另一人。确实没有合格目标且确认尚未提交时可结束本次尝试。
- 告知明确发送失败仍尝试转接。若告知结果尚不明确，随后又无目标可转，保持待核对，不解除可能仍在发送的操作。
- 转接成功须有匹配目标以及平台业务 `result=ok` 回执。执行前单次领取，提交后断线、超时或结果不明确标记 `confirmation_pending`，不自动重复提交。
- 操作状态另存于现有 RPA 任务表，防止普通会话快照覆盖转接屏障。旧排队回复取消，发送前再次校验；无人可接不会重新放出转接前积压的旧回复。
- 只有本次无人可接才放行后续咨询；独立设置的人工标记、真实查询失败、已成功转接或结果待核对不被这条规则清除。原有普通“待人工”标记的其他历史语义不作整体改造。
- 五分钟未完成或策略关闭会收敛未完成操作；可能已发送告知或已提交转接的保留待核对。转回自动恢复、视觉识别和逐类卡片解析暂不实现。

消息中心显示“暂无其他可接待客服，本次未转接；新消息仍会自动处理”，也显示进行中、已转出和待核对状态。
